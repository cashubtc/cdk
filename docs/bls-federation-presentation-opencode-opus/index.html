03 Ground truth

Say this first, or lose the room.

We say “keyset v3”. The Rust enum says Version02. The hex ID starts 02. All three are the same thing, and the off-by-one is permanent.

second collision

Cashu already has TokenV3 / ProofV3. Those are token encoding versions. Nothing to do with BLS keysets. v3 proofs ship inside TokenV4.

04 Ground truth

One landing, then six corrections.

The shape of the precursor is instructive: every fix after the landing is about sampling scalars correctly or not panicking on a foreign curve. That is what adding a second curve to an old SDK actually costs.

the pattern

Three separate commits replace modular reduction with rejection sampling: mint amount keys, NUT-13 blinding factors, batch weights. Reducing raw bytes into Fr is biased and, for the batch weights, simply failed the published vector.

the one that matters most

289fe9e44 — wallets must verify the blind signature e(C_, G2) == e(B, K), not only the unblinded proof. Landed by callebtc, not the original author.

05 Keyset v3

You cannot split k in an additive scheme
and keep an ordinary proof.

secp DHKE works fine for one operator. It gives you no way to share the secret and still let a wallet verify against one public mint key. Pairings do. That is the whole reason BLS lands before federation.

The pairing equation is the hinge. A wallet checks a signature against the aggregate G2 key K and never touches k. Because the check does not need the secret, the secret can later be shared — the same equation verifies a member share and a finished proof.

where the points live

Mint keys in G2, 96 bytes compressed. Blinded messages and signatures in G1, 48 bytes. DST CASHU_BLS12_381_G1_XMD:SHA-256_SSWU_RO_.

scope limit — say it out loud

The original bls branch is single-signer. No shares, no Lagrange, no DKG, no keyset gates, no roster, no consensus. That all starts later.

nut01/bls.rs on bls

~326 lines: BlsSecretKey, BlsG1PublicKey, BlsG2PublicKey, pairing verify, blind-signature verify, batch verify with transcript weights. That is all.

06 Keyset v3

No new token format.
A third keyset version.

Id::v3_from_data() is the v2 commitment recipe with the version byte rewritten. Then DHKE, derivation, signing and verification all branch on keyset_id.get_version().

  1. sort public keys by amount
  2. concat amount:hex(pubkey) — the bytes are compressed G2, not secp
  3. append |unit:sat
  4. append |input_fee_ppk:… if set
  5. append |final_expiry:… if set
  6. SHA-256
  7. prefix version byte 02 instead of 01 → 33 bytes

Same width as v2. 33 bytes total. A wallet that already parses v2 IDs parses v3 IDs; only the curve behind the key bytes changed.

version matrix
 enumidcurve blindunblindverifydleq
v1Version0000+7secp256k1 Y+rGC_−rKsecpoptional
v2Version0101+32secp256k1 Y+rGC_−rKsecpoptional
v3Version0202+32BLS12-381 r·H(s)r⁻¹·C_pairingnone

Default mint policy. use_keyset_v2 = None → new keysets are v3. Some(true) → v2, Some(false) → v1. Existing active keysets are preserved: do not rotate a live secp keyset just because the binary learned about BLS.

rotation grew a version argument

Mint::rotate_keyset_by_version(..); fake-wallet accepts "v1"|"v2"|"v3"; mint-cli rotate-next-keyset --keyset-version v3. The boolean stays for compatibility, but the control plane is KeySetVersion.

proto is off by one

proto 1=v1, 2=v2, 3=v3. On the original branch the proto enum still only named V1/V2 while the Rust mapping already understood 3.

what the ID commits to

Unit, fee, expiry — and now a set of G2 amount keys. That property is what lets a federation later advertise an aggregate keyset that looks exactly like a standalone v3 keyset.

07 Keyset v3

Parsing by length.

PublicKey became a three-variant enum and the discriminator is the byte count. Identity and infinity points are rejected. BLS scalars are big-endian on the wire and reversed for bls12_381::Scalar.

the useful identity

SecretKey::public_key() on a BLS scalar returns the G2 mint key k · G2. One scalar, one advertised key, whether it is a standalone mint or the aggregate of a federation.

hash-to-curve, two worlds

secp keeps the Cashu loop: DST Secp256k1_HashToCurve_Cashu_, try even x-only keys until one lands on-curve. v3 uses standardized ExpandMsgXmd<Sha256> SSWU_RO, and hash_to_curve_for_version() is the switch behind Proof::y().

Secp256k1 33 B
BlsG1 48 B
BlsG2 96 B

G1 carries blinded messages, signatures and shares. G2 carries mint public keys and DKG commitments. secp carries P2PK, HTLC, member identity and, later, FROST.

still panics on a BLS variant · original-branch leftover

08 Keyset v3

Reduce, and you are biased.
Sample, and you are canonical.

Every deterministic v3 scalar — wallet blinding factors, mint amount keys, batch weights — is rejection-sampled from Fr*. Three commits on the precursor branch exist only to make that true.

attemptHMAC-SHA256 outputverdict
rejected canonical Fr*

v3 blinding factor. The attempt counter is appended inside the HMAC message, so the sequence is reproducible from the seed alone. All-zero is rejected; a non-canonical scalar is rejected; the first canonical non-zero output wins.

wallet · NUT-13

// Secret::from_seed
v1        BIP32 path
v2 & v3   "Cashu_KDF_HMAC_SHA256" ‖ keyset_id
          ‖ u64_BE(counter) ‖ 0x00

// SecretKey::from_seed — blinding factor
v1        BIP32 path, child 1
v2        same KDF, suffix 0x01 → secp
v3        same KDF, suffix 0x01
          ‖ u32_BE(attempt) → canonical Fr*

mint · NUT-02 · MintKeySet::generate

  1. SHA-256 the BIP32 child, then reduce into Frfeat: bls
  2. reduce the BIP32 child bytes directly1d71add6e
  3. rejection-sample a second hardened index59a7a80e5
for amount index i:
    attempt = 0
    loop:
        child = BIP32(i' / attempt')
        reject all-zero
        accept SecretKey::bls_from_slice(child)

A unit test pins the live key to the two-level rejection-sampled child, not the old reduced one-level child. Random ephemeral scalars use the same sampler over OsRng via generate_bls().

restore follows the curve for free

PreMintSecrets::from_seed and blank change outputs call blind_message_for_version(.., keyset_id.get_version()), so deterministic minting and restore pick the right curve without a single extra branch at the call site.

09 Keyset v3

Two pairing gates, not one.

Correct v3 verification checks the blind signature before trusting the mint response, then checks the unblinded proof. Early wallet code did only the second one. That was the bug in 289fe9e44.

wallet G1 blinded / signature G2 verification rejected the public HTTP/WS protocol does not change

what the fix wired up

verify_bls_blind_signature() into wallet/blind_signature.rs, restore, auth-wallet mint, and verify_token_signatures (verify_token_dleq kept as a deprecated alias). Receive and issue sagas verify with pairings after unblinding.

tokens did not change

v3 proofs are ordinary Cashu proofs. Two serialization details: ProofV4.dleq is now skip_serializing_if, and a test asserts a v3 token does not encode an empty DLEQ (0x61 0x64 0xf6 / "d": null).

mint side

cdk-signatory verify_proofs() checks spends with verify_bls_message and rejects leftover DLEQ on v3 proofs. Proof::y() is version-aware.

10 Keyset v3

A valid G1 point is valid hex.

P2PK and HTLC stay secp-only. But a compressed G1 point parses cleanly through PublicKey::from_slice, so an attacker can put one in nut10 spending condition data. Before the fix, that panicked.

before 2dedc3ca7

verify_p2pk → x_only_public_key() → panic on a perfectly well-formed BLS point in data, pubkeys or refund_keys.

after

Error::NonSecp256k1Pubkey. A typed error, not an aborted process.

why fuzzing had to change

Random hex almost never decodes to a subgroup-correct BLS point, so a naïve fuzzer would never reach the bug. The targets inject valid points on purpose.

Everything so far,

These four cover main..bls completely. Federation starts after this line, and mixing them is the single biggest risk in the talk.

Why BLS before federation

Show the secp equations, then the pairing equations. The point: we needed a scheme where wallets verify against one public key while the secret can later be shared. Stay explicit that the original branch is still single-signer.

Keyset v3 is the protocol switch

13 The fork

Single‑signer ends here.

Federation mode is v3/BLS-only. v1, v2 and non-BLS aggregate keysets are rejected outright. Everything after this page is the bls-federation layer.

what got added on top of nut01/bls.rs

Threshold types. Dealer-free BLS DKG. Federated keyset rotation. Share verification. Wallet aggregation of member shares into ordinary Cashu proofs.

a separate key hierarchy, on purpose

Bitcoin custody — FROST, BDK, Bark — is not the Cashu BLS keyset. Different curve, different key, different job. Do not let them collapse into one “threshold secp everywhere”.

the next research pass, in order

  1. threshold BLS primitives
  2. v3-only federation keyset gates
  3. DKG and keyset rotation
  4. wallet share aggregation
  5. consensus, payments, transport

secp could have done it.
It would have federated the wrong thing.

Move the slider and watch which object changes shape. The bundle is the bearer instrument, so every later hop — receive, swap, melt, restore — has to understand it.

bare multisig · option 1

Each member has its own secp key k_i. Wallet blinds once. Each member returns a full C_i = k_i · B_, plus DLEQ if you want public verifiability. A spendable proof carries t signatures.

interpolated secp DHKE · option 2

Secret-share one secp key. Each member returns C_i = k_i · B_. Wallet Lagrange-interpolates C = Σ λ_i C_i and gets one ordinary secp proof under K = kG. BLS is option 2 on a pairing curve — not option 1 with nicer bytes.

the honest summary

Naive secp multisig federates the token. BLS threshold federates the issuer, then emits a normal token. Cashu cares about the second thing. The bearer object should stay boring.

16 The fork

Three ways to build it.
Two of them leak.

Bitcoin can afford bare multisig because the coin lives in a UTXO that already names its script. Cashu cannot, because the coin is the signature.

Why option 2 is still worse than BLS. EC addition interpolates fine — that is not the hard part. The hard part is proving the interpolated point really is k · Y under the advertised aggregate key, when nobody has k. Standalone Cashu proves that with DLEQ, and DLEQ uses the mint secret.

No extra DLEQ. No third-party verifier that has to understand the roster. That is why the original BLS branch forbids DLEQ on v3: pairings replaced it.

what naive multisig would still get right

Blindness works — members only ever see B_. t-of-n availability works. For a trusted 2-of-3 prototype among people who all run custom wallets, it is less crypto work up front. And the expensive part — consensus, replay, catch-up, payment observation, “do not sign until accepted” — does not go away either way.

17 Threshold

Classic Shamir,
on a blinded G1 point.

One secret mint scalar k per denomination is split. Any t members reconstruct one ordinary v3 blind signature. Fewer than t learn nothing useful. Signer IDs are non-zero u16 — zero is forbidden because f(0) is the secret.

signers
—

Toggle any two signers. The line through their shares always hits the same intercept.

the same example, with the Lagrange arithmetic

f(x) = 7 + 3x        M1 + M2   λ1 = (0−2)/(1−2) = 2
k  = f(0) = 7                λ2 = (0−1)/(2−1) = −1
k1 = 10  k2 = 13  k3 = 16      C = 2·(10B) − 1·(13B) = 7B

                      M2 + M3   λ2 = 3, λ3 = −2
                               C = 3·(13B) − 2·(16B) = 7B

Member 1 alone holds 10B, not 7B. The in-tree 3-of-5 test does this with real BLS scalars: subsets {1,3,5} and {2,3,4} both equal the dealer secret times B. 

f(x) = a0 + a1·x + … + a_{t-1}·x^(t-1)   deg t−1
a0 = k

k_i = f(i)          member i's share
K_i = k_i · G2      published, per member
K   = k · G2 = f(0) · G2   the v3 keyset

C_i = k_i · B       member signs the blinded point
e(C_i,G2) == e(B,K_i)  anyone can check

λ_i(0) = Π_(j∈S, j≠i)  (−j) / (i − j)
C = Σ_(i∈S) λ_i(0) · C_i = f(0) · B = k · B

Interpolation in the exponent. Any valid subset of size t gives the same C; order does not matter; duplicate signer IDs and short sets are rejected. A 1-of-1 keyset is exactly a normal single-signer BLS key — the tests assert it.

what this is not

Not bare multisig — the token never keeps C_1…C_t. Not FROST — that is the later secp Bitcoin-custody scheme. Not IETF BLS aggregation of different messages — every share here is a share of the same k · B.

two ways to create the shares

Trusted dealer picks the coefficients and hands out k_i — used in tests. Dealer-free Pedersen DKG: every member picks its own polynomial and the joint secret is the sum of the a0s. Same math afterwards.

18 Threshold

Every share is independently valid.
That is the whole problem.

C_i = k_i · B checks out against member i's published share even if nobody else ever saw that B. So show different members different output sets and rotate who sees which window.

paid 3 · minted 0

3-of-5. The quote paid for 3 notes. Each member only ever sees a balanced 3-output request.

the quorum cover, written out

M1 signs A B C        A: M1, M3, M4, M5   ≥3
M2 signs B C D        B: M1, M2, M4, M5   ≥3
M3 signs C D A        C: M1, M2, M3, M5   ≥3
M4 signs D A B        D: M2, M3, M4       =3
M5 signs A B C
                      four finished proofs from a 3-token payment

the name to use

The motivating attack is threshold-signing mix-and-match: a wallet presents different outputs or requests to different members and combines overlapping share subsets. docs/federated-cashu-rfc.md

Informal talk says sliding window. Other docs say overlapping-window mix-and-match, sliding-window quorum-cover, threshold-signature mix-and-match. Use threshold-signing mix-and-match for the attack, and sliding window for the picture. The regression suite is runtime_config_rejects_sliding_window_mint_output_attack and local_federated_members_reject_sliding_window_swap_output_attack.

it works on swap too

Keep the inputs fixed and slide the output set. The inputs get spent once in each member's local view, but the wallet reconstructs extra change or extra swap outputs from the overlapping shares.

not a BLS bug

This is what happens when a threshold issuer signs before it agrees on the exact message. Consensus is the fix. Members must sign only the one canonical operation that won ordering.

19 Threshold

A member does not sign because
it got an HTTP request.

It signs because that exact envelope came out of the ordering box as accepted. Treat AlephBFT as a black box: envelopes in, one total order out.

Swap · inputs P1 P2 → outputs A B
S_AB = hash(envelope) = 7c1e…a04b
not submitted
Swap · inputs P1 P2 → outputs B C
S_BC = hash(envelope) = 2f90…d117
not submitted
idle

Same bytes, same ID. Change one output, different ID. The box can only accept one first — and it will not accept a second live swap of P1 P2, because those proofs are already spent in the accepted history.

mint / melt lock vs swap lock

Mint and melt conflict on the quote ID: two output sets for one paid quote are the same conflict key and different operation IDs, so the second is rejected as a conflict. Swap has no quote — the inputs themselves become the lock once the first accepted swap spends them. Same result either way.

a swap is a named envelope

envelope = {
  federation,
  kind: Swap,
  inputs:  [P1, P2],
  outputs: [A, B]
}
operation_id = hash(envelope)
  1. wrap the ordinary Cashu SwapRequest as that envelope
  2. submit it to the consensus box
  3. wait until that exact ID is accepted
  4. only then spend the inputs and return BLS shares for those outputs

why T can sit below C

A 3-of-5 signing threshold with 4-of-5 BFT is safe only because shares are produced after the exact operation is accepted. Sign first and order later, and the lower threshold brings mix-and-match straight back.

20 Two planes

Two networks.
Same members, two topologies.

The public plane is wallet→mint and it is a star. The private plane is member↔member and it is a mesh. HTTP and Iroh are just two pipes for the same two planes — iroh://… is not a new protocol.

The wallet is the hub and the aggregator. Members never send shares to each other.

one swap, across both planes, in time

  1. wallet fans swap(P1,P2 → A,B) to everyone public
  2. each member that hears it submits the same hashed envelope private
  3. the box eventually says: S_AB is accepted private
  4. each ready member spends P1 P2 and returns shares for A B only public
  5. wallet aggregates → one ordinary v3 proof per output

private plane · /federation/v1

A second URL, federation_api_url, authenticated with the member identity key. Wallets should not be on it. It carries consensus — submit envelope, AlephBFT frames, peer status, catch-up — and later the whole DKG ceremony.

the split that matters

Not HTTP vs Iroh. Public fan-out vs private mesh. Tests already dial a roster where some members are HTTP and some are Iroh from one transport. The Axum router is reused either way.

21 Two planes

Hash so nobody can adapt.
Reveal so everyone can check.
Then add.

Dealer-free Pedersen DKG. Every member picks its own polynomial; the joint secret is the sum of the constant terms. The mint key k never exists in one place, and the wallet still sees one ordinary v3 keyset at the end.

—

Step through the ceremony. It runs on the private member mesh, not on the wallet fan-out.

once per denomination

A Cashu keyset is one key per amount. Same ceremony, many polynomials. Members also publish K_i = k_i · G2 — that is how a share is checked later without reconstructing k.

transcript, then activation

Hash the finished public ceremony, collect member signatures, then activate the keyset.

The aggregate public key is the same addition as the secret shares, but only over the constant terms revealed in the open. A lie in a private evaluation is visible, because it fails against the sender's committed polynomial.

22 Money & holes

Consensus authorizes a member,
not the owner of the proofs.

Fan-out is how a Byzantine member learns the bearer proofs. Nothing in the envelope proves the proof owner wanted those outputs. Audit name SEC-2026-07-17-01. Still a production blocker.

wallet fans P1,P2 → A,B to M1…M5
evil M5 copies P1,P2 · builds P1,P2 → X,Y · submits it first
consensus winner: P1,P2 → X,Y · balanced, well-formed, member-signed
honest members spend P1,P2 · BLS-sign X,Y ← attacker outputs
wallet P1,P2 → A,B fails: TokenAlreadySpent
with SIG_ALL witness commits to A,B → X,Y is not a valid spend

The database still prevents two committed spends — so the outcome is not double issuance, it is theft. The attacker's spend wins and the user's spend loses. Honest members cannot tell that X, Y were not the user's outputs, because nothing in the operation says who the owner is.

what this is not

  • not a BLS bug — the shares are valid, they are for the wrong outputs
  • not mix-and-match — only one operation wins, and it is the attacker's
  • not solved by fan-out — that is how the evil member learned the proofs
  • not solved by DKG — DKG protects k, not bearer secrets

status · say this plainly

Current code can bind SIG_ALL when the user already used it, and tests prove an output mutation changes the operation ID and fails apply. It does not require it on every federated spend — so until that decision is made, this federation is not safe for users against one malicious member.

how a federated swap is authorized today

  1. wallet fans the full SwapRequest to every member — including the raw input proofs
  2. the receiving member wraps it and authorizes it with the member identity key
  3. consensus checks that a roster member signed the envelope
  4. nothing checks that the proof owner signed those exact outputs

Authorized as “a federation member said this swap should happen”, not “the owner of these proofs wanted these outputs”. For an ordinary bearer proof, seeing the request is enough to build another valid spend. Melts have the same shape — quote conflict keys are not client authorization.

why SIG_ALL is the Cashu-shaped fix

NUT-11 already has the tool: lock the proof to P2PK and sign with SIG_ALL. That witness commits the owner to the exact outputs, so admission and apply can reject the rewritten swap before it becomes the accepted operation. The evil member still sees the proofs — it just cannot produce a different valid spend.

why a detached key does not help

The owner has to bind the spend at proof-creation time, or at least with a secret the receiving member does not already have from the request itself. If ordinary unlocked bearer proofs stay supported, one receiving member remains trusted not to steal them.

23 Money & holes

A committee printing IOUs against
a piggy bank one person holds.

A Cashu mint is two machines glued together: the eCash issuer and the funding backend. Federate only the first and you have not built a federation.

BLS · blinded Cashu signatures FROST · Bitcoin/Lightning the outside world understands do not mix the secrets

what one operator could do

Point every member at one CLN

Mark a quote paid when nothing arrived, and the BLS side issues eCash. Refuse a melt, or pay a different invoice. Sweep the on-chain or Lightning funds while the eCash ledger still looks honest. The other members can vote all they want — they cannot stop a key they do not share.

federated BDK · on-chain treasury

Nobody loads a mnemonic

Members watch the chain, agree addresses and unsigned transactions through the same consensus box, then jointly sign. One member can propose “send these coins to this melt address”. It cannot move them.

federated Bark · Lightning treasury

Claiming is a custody action

Incoming invoices and outgoing payments are planned as consensus operations first. Claiming an HTLC or sending a payment is a threshold action, not “member 3's node paid it”.

fakewallet and development_single_observation

They explicitly trust one local observation. That is a test fixture, not a federation funding model. A production policy has to require a member quorum and the backend itself has to be threshold-held — quorum observations against a single-key CLN still leave one trusted operator. Classical single-mint connectors are fine for standalone CDK; in a federation they reintroduce a king.

24 Money & holes

Two ceremonies.
Startup is not done until both finish.

BLS DKG makes the eCash mint key. FROST DKG makes the treasury key. Same roster, same ceremony ID, same signature_threshold — on purpose, because the people who can issue eCash must be the people who can move the reserves. 

setup
  ├─ BLS DKG   → k_i, K     Cashu proofs
  └─ FROST DKG → s_i, P     Bitcoin / Lightning

FROST rounds  private member plane
  1. broadcast polynomial commitments + proofs   /dkg/frost/round1
  2. per-recipient confidential contributions    /dkg/frost/round2
  3. every member confirms the same public P

then
  any t members → ordinary BIP340 Schnorr under P
  never reconstruct the private key

frost-secp256k1-tr 3.0.0, isolated in cdk-frost. Ciphersuite secp256k1_sha256_tr_v1, protocol version 2, member IDs map 1:1 onto FROST identifiers. Every message binds federation ID, ceremony ID, setup authorization, root epoch, protocol, ciphersuite, threshold, ordered roster, sender and receiver — BLS and FROST transcripts cannot be confused.

persist-before-send

Sealed local phase state is written before any dependent outbound package. Exact replay is idempotent; a second different payload for the same ceremony/kind/sender/receiver is equivocation. A phase does not advance until the whole outbound batch is acknowledged, so a partition cannot leave one member holding a package another member never got.

at rest

The local signing share is AES-256-GCM ciphertext. Public records never contain a plaintext share. Associated data binds the ciphertext to phase, member, ceremony, sender/receiver, and the public root package.

what comes out · public root package

  • root epoch, protocol, ciphersuite, threshold
  • ordered member → verification-share map
  • full compressed group key P
  • transcript binding

local package, sealed

Only that member's signing share s_i. No mnemonic, no BDK descriptor, no Bitcoin network, no child index, no Taproot tweak, no BLS material. The root is untweaked and application-neutral.

applications derive later, in this exact order

  1. canonical untweaked root
  2. application-domain additive tweak
  3. domain-separated public chain code
  4. non-hardened BIP32 branch and child
  5. BIP340 even-Y normalization during FROST signing
  6. BIP341 key-path-only Taproot tweak, on-chain

Bark and BDK are consumers of this root. They do not run a second DKG for the treasury key.

25 Operations

Two public calls.
Everything safe is behind them.

Wallet APIs stay Cashu. The private plane carries submit-envelope, peer status, catch-up, chain observations, address allocation, transaction proposal, FROST rounds, signed-tx and broadcast intent. make_payment does not send coins.

mint · on-chain method

POST mint quote, amount + method. Connector tries the first healthy member, not full fan-out.

That member does not call reveal_next_address(). It submits MintQuote AllocateAddress — binding quote, application epoch, external keychain, next unused index.

After accept, every honest member derives the same address from the FROST/BIP32 descriptor. The response is ordinary Cashu: quote id + address.

Wallet fans quote-status until a threshold can see that same quote. One member's invoice is not enough.

User pays. Watch-only BDK wallets see a UTXO. That is a cache, not truth.

Each member submits ChainObservation::Deposit — exact outpoint, amount, script, block, depth, allocation. A minority cannot mark money received.

Only then do MintQuotePayment observations finalize amount_paid. Two incompatible quorums leave the quote unpaid.

Wallet polls (fan-out). When paid, POST /mint with blinded outputs to every member.

Each member wraps the exact outputs as Mint, waits for accept, returns a BLS share. Conflict key is the quote. Wallet verifies against K_i and interpolates one v3 proof.

Checks that matter. The address is consensus-owned. Mempool is not payment. A reorg before issuance unsays the UTXO; a reorg after issuance raises an alarm and does not unmint. Issuance still requires the paid quote and the exact output set.

melt · destination address

POST melt quote with a Bitcoin address. First healthy member, then threshold visibility.

POST /melt with proofs and optional change, fan-out. Melt accept means: proofs reserved/spent, change bound, on-chain payment intent created.

Consensus does not take a PSBT on faith. TransactionProposal carries the exact unsigned tx: inputs, prevouts, destination, amount, fee, weight, sighashes, optional change to a consensus-allocated internal address.

Every member recomputes ownership, value conservation, fee caps, destinations, Taproot sighashes. Conflict keys lock the batch, each UTXO, each intent. Sticky reservations: ambiguous broadcast still keeps coins reserved.

FROST starts after accept. Per input, authorization binds operation + tx + input index + the exact 32-byte sighash. Coordinator only aggregates. Nonces go vacant → reserved → published → consumed; failures burn.

TransactionSigned persists the exact signed bytes before anyone talks to Bitcoin. Then BroadcastIntent for those bytes only. Observations cannot swap in another txid.

Confirmation observations to quorum and depth, then MeltQuotePayment marks paid. Change shares aggregate like mint shares.

Checks that matter. One member cannot redirect the payout, sign a different tx, broadcast unsigned or alternate bytes, or spend a UTXO that is not accepted-and-spendable. Change, if any, is BLS and only for the accepted melt.

26 Operations

A federated swap never
touches Bitcoin.

No quote, no BDK, no FROST. Only eCash: spend old proofs, issue new ones. The wallet API is still an ordinary POST /swap, and the response looks like a SwapResponse — except the “signatures” are that member's BLS shares.

Wallet holds P1 P2, blinds A B. The connector validates the outputs against the advertised v3 keysets, then fans the same SwapRequest to every member's public_mint_url.

Each ready member wraps it as {federation, kind: Swap, request} → operation_id = hash(envelope). Admission rejects empty inputs, duplicates, non-v3 outputs, oversized witnesses and unbalanced amounts before proposing.

It does not sign yet. submit_federation_envelope: check local readiness / catch-up, then put the envelope in the box. Lagging members fail closed and return no shares.

Others hear the same envelope through AlephBFT, or submit the identical operation_id because the wallet posted to them too. Exact retries are idempotent.

The box accepts one winner — say S_AB.

Every honest member applies that entry: verify inputs against the aggregate v3 keys including P2PK/HTLC/SIG_ALL; check the tx balances after fees; mark P1 P2 spent; persist A B; produce C_i = k_i · B only for the accepted outputs, bound to operation ID, member, keyset, amount and output index.

persisted_swap_share_response — this member's shares for S_AB, never a standalone final signature.

The wallet does not wait for everyone. It needs a signature threshold of shares for the same outputs, checks each with e(C_i,G2)=e(B,K_i), Lagrange-interpolates one C per output and unblinds into ordinary v3 proofs.

If a subset instead saw P1,P2 → B,C, that is S_BC: a different envelope, which cannot collect shares after S_AB is accepted. That is the sliding-window defense, in one sentence.

guarantees

  • only one exact input/output set can be signed
  • inputs are spent once, across the roster
  • shares exist only after accept, and only for the accepted outputs
  • restore later returns those same shares, never new ones
  • offline members can catch up and still serve the accepted shares — they cannot invent another window

not guaranteed, unless the proofs already use SIG_ALL

  • a Byzantine member who saw the bearer proofs can rewrite P1,P2 → X,Y and race that envelope first

already frozen · each implies a new federation

  • add, remove or replace a member — no membership op; BLS and FROST shares do not transfer
  • rotate a member identity key — it authenticates private REST and it is in the ID
  • change T or C — thresholds are genesis; 3-of-5 → 4-of-7 is a new mint
  • change observation quorum, Bitcoin network, confirmation depth, fee policy or FROST epoch

still open

Locator vs identity — today they are glued. A future design could hash only member ID + identity key and treat URLs as a rotatable, authenticated advertisement. That is the real fix for DNS and it does not exist yet.

also open

Genesis vs policy (should quorum, cadence, fee caps be a config-amendment op?). Member repair vs seat replacement. A “same mint, new URL” story for users. Partial transport failure — both URLs are genesis, so you cannot fail over to a backup name.

Consensus does not elect new members and does not update DNS. Keyset rotation changes what eCash key signs. Almost everything else is setup-time law.

29 Constitution

Peers can give you the book.
Only your backup gives you the pen.

There is no BIP39 seed that regenerates a federation member. A member is a named roster seat holding unique secrets. Lose them and you do not restore the node — you replace the federation.

Restore cookbook. Process died, disk fine → start mintd; if it stays fail-closed it needs catch-up, not a new identity. Disk lost with secrets + quiesced backup → restore DB, configs, sealed FROST, manifest, audit, then catch up to tip. Disk lost, only secrets → empty DB and genesis page catch-up. Secrets lost → stop. Do not copy another member's private config.

fail-closed is the safety valve

Public mint/swap/melt, FROST commitments and shares, payment observations and broadcast all require: not lagging, not catching up, not halted, checkpoint/audit OK. A half-restored node does not sign.

the pen · cannot be caught up from peers

  • MemberConfigPrivate: member_id, secp identity secret, keyset_secret_shares for every amount of every keyset — including rotated inactive ones — and the setup transcript hash they came from
  • sealed FROST root share plus the sealing key generation that can open it
  • Bark receive secrets / mailbox keys, and TLS / Iroh node keys

the book · quiesced snapshot + manifest

Journal from genesis (v1 retains index 0), finalized AlephBFT bodies, materialized Cashu state, address/UTXO/intent projections, checkpoint quorums, active session backup, schema contract, durable frontier cursors. The backup-manifest is checked before serving traffic — no bypass flag.

two digests, both bound

The chain of operations has an order digest; deterministic DB state has a materialized-state digest. A peer with the same journal but a different SQL projection is not caught up. Catch-up needs a consensus-threshold certificate quorum, then replay, then both digests.

the audit latch has no force-clear

If state ≠ digest, the member latches failed. Restart, peer agreement and checkpoint promotion do not clear it. Preserve the bad DB, restore a known-good generation or genesis-replay with the same secrets, audit again.

three sentences to remember

Pairings replaced DLEQ, which is why v3 forbids it. Consensus is the agreement; BLS is only the compact way to emit an already-agreed signature. The quorum that can issue eCash must be the quorum that can move the reserves.

and one honest caveat

Until SIG_ALL — or an equivalent client spend-intent binding — is required on federated spends, do not describe this federation as safe for users against one malicious member.

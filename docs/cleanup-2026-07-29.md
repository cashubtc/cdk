# Federation cleanup execution ledger — 2026-07-29

## Purpose

This document is the controlling implementation ledger for the current BLS
federation cleanup. It reconciles the federation implementation plan, the
latest cleanup/refactor plan, the security reviews, the database and wallet
reviews, the BDK review, and the most recent AlephBFT and Bark/FROST work with
the code that exists on this branch.

The work is not complete merely because a patch exists. Every item below must
first be independently reassessed against the current code, and every retained
fix must be proven by focused regression coverage plus proportionate wider
validation. A candidate that does not satisfy its acceptance criteria must be
removed before the milestone is closed.

This ledger is complete only when every milestone is in a terminal state and
the final verification milestone is complete.

## Mandatory issue protocol

Every milestone follows this sequence:

1. **Reproduce or locate the current behavior.** Record an executable
   regression, an existing failing check, or precise source-level evidence.
2. **Reassess value and scope.** Decide whether the issue remains real, whether
   the proposed remedy is safe and compatible, and whether it belongs in this
   cleanup.
3. **Choose the smallest sufficient fix.** Avoid opportunistic architecture
   changes unless the evidence shows they are needed for correctness or
   maintainability.
4. **Implement behind a focused proof.** Add a regression test before or with
   the fix whenever practical.
5. **Validate proportionately.** Run the focused test, the affected crate
   tests/checks, formatting for repository-owned files, and any relevant
   integration or feature matrix.
6. **Keep or roll back.** A candidate is successful only when its acceptance
   criteria pass. If it fails or creates unacceptable regressions, remove the
   candidate changes and record the failure and next decision here.
7. **Commit the terminal milestone.** Update this ledger with evidence and
   commit the code and ledger together. Do not combine unrelated milestones in
   one commit.

Documentation-only reassessments must still cite current-code evidence and get
their own milestone commit.

## Status vocabulary

- **Planned** — not yet reassessed against current code.
- **Reviewing** — evidence is being gathered; no fix is accepted yet.
- **Kept** — reassessed, implemented, and proven.
- **Superseded** — reassessed and already resolved by existing code.
- **Rejected** — reassessed and determined not worth or safe to implement.
- **Deferred** — confirmed, but a prerequisite or separately authorized
  project is required; the exact boundary and risk are recorded.
- **Blocked** — validation cannot run because of an external dependency; this
  is not terminal for the overall ledger.

`Kept`, `Superseded`, `Rejected`, and `Deferred` are terminal for an individual
milestone. The ledger may finish with a `Deferred` milestone only when its
remaining work cannot responsibly be completed within the repository without
new protocol, product, infrastructure, or compatibility authority.

## Priority model

Milestones are ordered by:

1. loss of funds or incorrect money state;
2. safety, equivocation, or threshold-signing authority;
3. wallet recovery and externally visible protocol consistency;
4. liveness and resource isolation;

critical diffs remain reviewable and their regression tests follow the code

## Milestone 1 — exact generic melt settlement accounting

**Status:** Kept

**Findings covered**

- SEC-2026-07-17-02
- Generic off-chain payment observations do not carry an authenticated
  `total_spent`.
- The current projection can use the entire fee reserve when the exact spend is
  not represented, which can burn valid change.

**Reassessment**

- Every generic `MakePaymentResponse` already carries the backend's exact
  `total_spent`; the loss occurred when the value was omitted while converting
  it into a federation observation.
- On-chain receipts and Bark action plans also contain an exact amount plus
  final fee, so all current paid-observation producers can supply the field.
- Matching authenticated observations remain the trust boundary: exact spend
  is now part of `matches_payment_evidence`, so conflicting member totals
  cannot form one quorum.
- An optional serialized field is required so historical version-5 journal
  entries still decode. Pure admission rejects new paid observations that omit
  it. Replay of a previously accepted legacy entry preserves its historical,
  conservative full-reserve result.

**Kept implementation**

- Added optional `total_spent` to
  `FederationMeltQuotePaymentObservation`.
- Paid observations are admitted only when the exact spend is between the
  requested amount and `amount + fee_reserve`. Non-paid observations must omit
  it.
- Generic, on-chain, and Bark producers populate exact spend; operation
  builders and direct federation routes preserve it.
- Melt finalization uses the agreed exact spend, leaving unused fee reserve as
  change.
- On-chain application cross-checks an asserted spend against the accepted
  receipt. Missing legacy values are tolerated only after the accepted-entry
  boundary and reproduce the former deterministic result.

**Proof required**

- [x] Regression: partial fee-reserve use returns the exact finalization amount.
- [x] Regression: conflicting member-reported final costs are different
  evidence and cannot form one quorum.
- [x] Regression: old serialized observations decode, fail new admission, and
  retain replay compatibility.
- [x] Regression: failed and pending observations omit exact spend and preserve
  compensation/transient behavior.
- [x] Affected federation operation/projection/melt tests pass.
- [x] Compatibility behavior is documented in the field, replay branch, and
  this ledger.

**Attempt history**

- The first candidate required `total_spent` inside the shared application
  helper for every observation state. The 143-test federation suite exposed
  three failed/rollback regressions because non-paid outcomes do not have a
  settlement amount. That part was removed. The retained design enforces exact
  spend at pure admission for paid observations, uses zero only in the
  non-paid in-memory response shape, and keeps the old full-reserve calculation
  solely for replay of already accepted legacy paid entries.

**Validation evidence**

- `cargo test -p cdk-common --features federation`: 457 passed, 1 ignored;
  four operation-auth integration tests and four FROST-DKG integration tests
  also passed.
- `cargo test -p cdk --features federation mint::federation::tests:: --
  --test-threads 1`: 143 passed.
- `cargo check -p cdk-mintd --features federation-test-utils`: passed.
- `cargo check -p cdk-axum --tests --features federation-bark`: passed, with
  pre-existing warnings in the external Bark dependency.
- Repository-owned affected crates pass scoped rustfmt.

## Milestone 2 — durable and verified wallet melt-change recovery

**Status:** Kept

**Findings covered**

- CLEAN-004
- DB-004
- Restarted connectors lose in-memory `melt_change_outputs`.
- The fallback can interpolate parseable shares without proving they correspond
  to the blinded outputs originally sent by the wallet.

**Reassessment**

- `MeltOperationData` already durably stores `change_blinded_messages`, the
  derivation counter range, expected change amount, quote ID, and exact final
  input Ys.
- `MeltSaga::request_melt` writes that data and advances the saga to
  `MeltRequested` before calling the connector, so no wallet database migration
  is needed.
- Restart recovery does not need change from the quote-status response. It
  takes the persisted blinded messages through the output-bound restore path,
  validates the returned aggregate signatures, reconstructs the deterministic
  secrets/blinding factors, and only then records proofs.
- The connector fallback was nevertheless unsafe as an API boundary: when its
  in-memory quote/output map was gone, it interpolated any parseable,
  metadata-matching shares without knowing their blinded messages. Normal saga
  recovery would reject a bad final aggregate later, but the connector itself
  incorrectly presented it as verified.
- Review also found that a pending status without change removed retained
  outputs too early, causing later paid-status recovery to take that fallback.

**Kept implementation**

- Removed parse-only interpolation when a connector lacks retained outputs.
  The connector now preserves the threshold-agreed payment state but strips
  unverified change, allowing the wallet to recover it from durable saga
  outputs via restore.
- Retained output context is no longer removed by intermediate no-change or
  empty-change status responses. It is removed after verified aggregation.
- In-process recovery still verifies every share against the exact retained
  blinded output and member/keyset metadata, tolerating a malformed or
  Byzantine minority.
- Restart recovery continues to use the already-durable output-bound restore
  flow; no duplicated database record or schema migration was added.

**Proof required**

- [x] Restart regression with a fresh connector and exact persisted context.
- [x] Wrong-output shares are not returned by a rebuilt connector.
- [x] Wrong-member, wrong-amount, wrong-keyset, and wrong-index shares are
  rejected.
- [x] Threshold valid shares recover the exact expected signatures.
- [x] Crash between persistence and submission is retry-safe through the
  pre-request durable saga transition.
- [x] Existing wallet database/saga serialization covers the durable fields;
  reassessment proved that no new fields or migration are required.

**Attempt history**

- The first removal of the fallback exposed three integration failures. The
  failures proved a separate retention defect: a pending response with no
  change removed the original outputs before the later paid response. The
  premature removals were removed; the fallback itself was not restored.

**Validation evidence**

- `rebuilt_federated_connector_omits_unverified_melt_status_change_shares`
  passes with a threshold of well-formed shares over the wrong outputs.
- `federated_melt_status_recovery_ignores_malformed_change_share` and
  `federated_melt_status_recovery_ignores_wrong_change_share` pass while using
  retained exact outputs.
- `wallet::melt::saga::resume::tests`: 19 passed, including persisted-change
  restoration when paid status omits change and fail-closed ambiguous restore.
- `wallet::federation::tests`: 95 passed, including the local/fake/HTTP
  pending-to-paid paths that exposed the early-retention defect.
- Repository-owned CDK sources pass scoped rustfmt.

## Milestone 12 — BDK reorg proof and broadcaster supervision

**Status:** Planned

**Findings covered**

- The BDK observer may infer a reorg when a previously stored exact block is
  merely absent from a local observation, rather than proven disconnected.
- The federation broadcaster handles accepted transactions sequentially,
  performs external waits without complete deadlines, and runs as a detached
  task.

**Review questions**

- What BDK chain API can prove that a stored block is no longer in the best
  chain?
- How are temporary unavailability, unconfirmed state, deep reorg, and member
  disagreement represented?
- Which task owner should supervise broadcaster shutdown and failure?
- What concurrency is safe for transaction broadcast and confirmation?

**Candidate**

- Emit a reorg transition only from positive chain-disconnection evidence.
- Treat absence/temporary uncertainty as pending observation.
- Supervise the broadcaster with bounded concurrency, per-operation deadlines,
  cancellation, and surfaced fatal errors.

**Proof required**

- [ ] Temporary observer absence does not emit a reorg.
- [ ] A proven disconnected block emits the expected transition.
- [ ] Reconfirmation after a real reorg is deterministic.
- [ ] One stalled broadcast/confirmation cannot block unrelated transactions.
- [ ] Shutdown cancels/joins the task.
- [ ] Task failure is observable by the service owner.

**Decision boundary**

- If reliable disconnection proof requires a BDK or node API not available in
  supported versions, fail conservatively and record the precise upstream
  prerequisite rather than preserving a false positive.

**Rollback trigger**

- Roll back heuristics that turn lack of evidence into reorg evidence or task
  supervision that can silently drop accepted transactions.

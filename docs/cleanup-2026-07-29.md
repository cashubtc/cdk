# Federation cleanup execution ledger — 2026-07-29

## Purpose

This document is the controlling implementation ledger for the current BLS
federation cleanup. It reconciles the federation implementation plan, the
latest cleanup/refactor plan, the security reviews, the database and wallet
reviews, the BDK review, and the most recent AlephBFT and Bark/FROST work with
the code that exists on this branch.

The work is not complete merely because a patch exists. Every item below must
first be independently reassessed against the current code, and every retained
fix must be proven by focused regression coverage plus proportionate wider
validation. A candidate that does not satisfy its acceptance criteria must be
removed before the milestone is closed.

This ledger is complete only when every milestone is in a terminal state and
the final verification milestone is complete.

## Mandatory issue protocol

Every milestone follows this sequence:

1. **Reproduce or locate the current behavior.** Record an executable
   regression, an existing failing check, or precise source-level evidence.
2. **Reassess value and scope.** Decide whether the issue remains real, whether
   the proposed remedy is safe and compatible, and whether it belongs in this
   cleanup.
3. **Choose the smallest sufficient fix.** Avoid opportunistic architecture
   changes unless the evidence shows they are needed for correctness or
   maintainability.
4. **Implement behind a focused proof.** Add a regression test before or with
   the fix whenever practical.
5. **Validate proportionately.** Run the focused test, the affected crate
   tests/checks, formatting for repository-owned files, and any relevant
   integration or feature matrix.
6. **Keep or roll back.** A candidate is successful only when its acceptance
   criteria pass. If it fails or creates unacceptable regressions, remove the
   candidate changes and record the failure and next decision here.
7. **Commit the terminal milestone.** Update this ledger with evidence and
   commit the code and ledger together. Do not combine unrelated milestones in
   one commit.

Documentation-only reassessments must still cite current-code evidence and get
their own milestone commit.

## Status vocabulary

- **Planned** — not yet reassessed against current code.
- **Reviewing** — evidence is being gathered; no fix is accepted yet.
- **Kept** — reassessed, implemented, and proven.
- **Superseded** — reassessed and already resolved by existing code.
- **Rejected** — reassessed and determined not worth or safe to implement.
- **Deferred** — confirmed, but a prerequisite or separately authorized
  project is required; the exact boundary and risk are recorded.
- **Blocked** — validation cannot run because of an external dependency; this
  is not terminal for the overall ledger.

`Kept`, `Superseded`, `Rejected`, and `Deferred` are terminal for an individual
milestone. The ledger may finish with a `Deferred` milestone only when its
remaining work cannot responsibly be completed within the repository without
new protocol, product, infrastructure, or compatibility authority.

## Priority model

Milestones are ordered by:

1. loss of funds or incorrect money state;
2. safety, equivocation, or threshold-signing authority;
3. wallet recovery and externally visible protocol consistency;
4. liveness and resource isolation;

critical diffs remain reviewable and their regression tests follow the code

## Milestone 1 — exact generic melt settlement accounting

**Status:** Kept

**Findings covered**

- SEC-2026-07-17-02
- Generic off-chain payment observations do not carry an authenticated
  `total_spent`.
- The current projection can use the entire fee reserve when the exact spend is
  not represented, which can burn valid change.

**Reassessment**

- Every generic `MakePaymentResponse` already carries the backend's exact
  `total_spent`; the loss occurred when the value was omitted while converting
  it into a federation observation.
- On-chain receipts and Bark action plans also contain an exact amount plus
  final fee, so all current paid-observation producers can supply the field.
- Matching authenticated observations remain the trust boundary: exact spend
  is now part of `matches_payment_evidence`, so conflicting member totals
  cannot form one quorum.
- An optional serialized field is required so historical version-5 journal
  entries still decode. Pure admission rejects new paid observations that omit
  it. Replay of a previously accepted legacy entry preserves its historical,
  conservative full-reserve result.

**Kept implementation**

- Added optional `total_spent` to
  `FederationMeltQuotePaymentObservation`.
- Paid observations are admitted only when the exact spend is between the
  requested amount and `amount + fee_reserve`. Non-paid observations must omit
  it.
- Generic, on-chain, and Bark producers populate exact spend; operation
  builders and direct federation routes preserve it.
- Melt finalization uses the agreed exact spend, leaving unused fee reserve as
  change.
- On-chain application cross-checks an asserted spend against the accepted
  receipt. Missing legacy values are tolerated only after the accepted-entry
  boundary and reproduce the former deterministic result.

**Proof required**

- [x] Regression: partial fee-reserve use returns the exact finalization amount.
- [x] Regression: conflicting member-reported final costs are different
  evidence and cannot form one quorum.
- [x] Regression: old serialized observations decode, fail new admission, and
  retain replay compatibility.
- [x] Regression: failed and pending observations omit exact spend and preserve
  compensation/transient behavior.
- [x] Affected federation operation/projection/melt tests pass.
- [x] Compatibility behavior is documented in the field, replay branch, and
  this ledger.

**Attempt history**

- The first candidate required `total_spent` inside the shared application
  helper for every observation state. The 143-test federation suite exposed
  three failed/rollback regressions because non-paid outcomes do not have a
  settlement amount. That part was removed. The retained design enforces exact
  spend at pure admission for paid observations, uses zero only in the
  non-paid in-memory response shape, and keeps the old full-reserve calculation
  solely for replay of already accepted legacy paid entries.

**Validation evidence**

- `cargo test -p cdk-common --features federation`: 457 passed, 1 ignored;
  four operation-auth integration tests and four FROST-DKG integration tests
  also passed.
- `cargo test -p cdk --features federation mint::federation::tests:: --
  --test-threads 1`: 143 passed.
- `cargo check -p cdk-mintd --features federation-test-utils`: passed.
- `cargo check -p cdk-axum --tests --features federation-bark`: passed, with
  pre-existing warnings in the external Bark dependency.
- Repository-owned affected crates pass scoped rustfmt.

## Milestone 2 — durable and verified wallet melt-change recovery

**Status:** Kept

**Findings covered**

- CLEAN-004
- DB-004
- Restarted connectors lose in-memory `melt_change_outputs`.
- The fallback can interpolate parseable shares without proving they correspond
  to the blinded outputs originally sent by the wallet.

**Reassessment**

- `MeltOperationData` already durably stores `change_blinded_messages`, the
  derivation counter range, expected change amount, quote ID, and exact final
  input Ys.
- `MeltSaga::request_melt` writes that data and advances the saga to
  `MeltRequested` before calling the connector, so no wallet database migration
  is needed.
- Restart recovery does not need change from the quote-status response. It
  takes the persisted blinded messages through the output-bound restore path,
  validates the returned aggregate signatures, reconstructs the deterministic
  secrets/blinding factors, and only then records proofs.
- The connector fallback was nevertheless unsafe as an API boundary: when its
  in-memory quote/output map was gone, it interpolated any parseable,
  metadata-matching shares without knowing their blinded messages. Normal saga
  recovery would reject a bad final aggregate later, but the connector itself
  incorrectly presented it as verified.
- Review also found that a pending status without change removed retained
  outputs too early, causing later paid-status recovery to take that fallback.

**Kept implementation**

- Removed parse-only interpolation when a connector lacks retained outputs.
  The connector now preserves the threshold-agreed payment state but strips
  unverified change, allowing the wallet to recover it from durable saga
  outputs via restore.
- Retained output context is no longer removed by intermediate no-change or
  empty-change status responses. It is removed after verified aggregation.
- In-process recovery still verifies every share against the exact retained
  blinded output and member/keyset metadata, tolerating a malformed or
  Byzantine minority.
- Restart recovery continues to use the already-durable output-bound restore
  flow; no duplicated database record or schema migration was added.

**Proof required**

- [x] Restart regression with a fresh connector and exact persisted context.
- [x] Wrong-output shares are not returned by a rebuilt connector.
- [x] Wrong-member, wrong-amount, wrong-keyset, and wrong-index shares are
  rejected.
- [x] Threshold valid shares recover the exact expected signatures.
- [x] Crash between persistence and submission is retry-safe through the
  pre-request durable saga transition.
- [x] Existing wallet database/saga serialization covers the durable fields;
  reassessment proved that no new fields or migration are required.

**Attempt history**

- The first removal of the fallback exposed three integration failures. The
  failures proved a separate retention defect: a pending response with no
  change removed the original outputs before the later paid response. The
  premature removals were removed; the fallback itself was not restored.

**Validation evidence**

- `rebuilt_federated_connector_omits_unverified_melt_status_change_shares`
  passes with a threshold of well-formed shares over the wrong outputs.
- `federated_melt_status_recovery_ignores_malformed_change_share` and
  `federated_melt_status_recovery_ignores_wrong_change_share` pass while using
  retained exact outputs.
- `wallet::melt::saga::resume::tests`: 19 passed, including persisted-change
  restoration when paid status omits change and fail-closed ambiguous restore.
- `wallet::federation::tests`: 95 passed, including the local/fake/HTTP
  pending-to-paid paths that exposed the early-retention defect.
- Repository-owned CDK sources pass scoped rustfmt.

## Milestone 3 — safe federation threshold profiles

**Status:** Kept

**Findings covered**

- SEC-2026-07-17-04
- Current validation primarily checks numeric relationships and can accept
  operationally unsafe threshold profiles.

**Review questions**

- Which threshold policies are protocol invariants versus deployment policy?
- Must development/single-member configurations remain possible?
- What Byzantine fault model is claimed by production defaults?
- Can unsafe profiles be represented only behind an explicit development
  opt-in rather than silently accepted?

**Reassessment**

- `ThresholdParams::validate` is a structural format check used by deterministic
  test runtimes as well as production code. Making it silently impose one
  deployment policy would invalidate intentional test and specialist profiles.
- The production model is already explicit elsewhere:
  `f = floor((n - 1) / 3)` and the default consensus quorum is `n - f`.
  Under that claim, signing needs at least `f + 1` members and two accepted
  consensus quorums need an intersection larger than `f`.
- Production DKG setup already derives `n - f`, but previously accepted
  `signature_threshold <= f`. Mint startup could also load a structurally valid
  config whose consensus threshold was below `n - f`.
- The existing
  `federation.allow_development_payment_observation_policy` switch is already
  loudly documented as local-development/regtest-only. It is therefore the
  compatibility boundary for an intentionally weak member runtime; wallet
  imports have no unsafe override because clients must not silently reduce
  their trust assumptions.

**Kept implementation**

- Added `ThresholdParams::validate_bft_safety`, separate from structural
  validation, and a structured `UnsafeThresholdProfile` error containing the
  configured values, modeled fault budget, and required minima.
- Production member startup and pre-start DKG reconciliation require
  `signature_threshold >= f + 1` and `consensus_threshold >= n - f`.
  The existing local-development switch is the only explicit runtime escape
  hatch and logs a warning.
- Production DKG roster assembly rejects unsafe signing thresholds before
  writing a roster.
- CLI federation wallet registries reject unsafe profiles on import and every
  subsequent load. Programmatic deterministic connectors can still use the
  structural API for test runtimes.
- Updated the mintd setting and example-config documentation to state that its
  development override also covers below-BFT threshold profiles.

**Boundary table**

| Members `n` | Modeled `f` | Signing / consensus | Result |
| ---: | ---: | ---: | --- |
| 2 | 0 | 1 / 2 | accepted |
| 3 | 0 | 1 / 3 | accepted; this profile claims no Byzantine tolerance |
| 4 | 1 | 1 / 3 | rejected; signing threshold does not exceed `f` |
| 4 | 1 | 2 / 2 | rejected; consensus quorum is below `n - f = 3` |
| 4 | 1 | 2 / 3 | accepted |
| 5 | 1 | 2 / 4 | accepted |
| 7 | 2 | 2 / 5 | rejected; signing threshold does not exceed `f` |
| 7 | 2 | 3 / 5 | accepted |

**Proof required**

- [x] Boundary table for accepted and rejected `(n, threshold)` profiles.
- [x] Existing valid production fixtures continue to load.
- [x] Unsafe profiles fail with structured, actionable errors.
- [x] Explicit development override is tested.
- [x] Config parsing and daemon startup tests pass.
- [x] Exhaustive `n = 2..64` arithmetic proves that every accepted production
  consensus quorum has minimum pairwise intersection greater than `f`.

**Validation evidence**

- The 64 focused `cdk-common` federation configuration/DKG tests pass.
- The 39 `cdk-cli` tests under the federation-only feature profile pass,
  including registry rejection of an unsafe but structurally valid profile.
- The focused mintd startup override regression passes, and
  `cargo check -p cdk-mintd --features federation --all-targets` passes.
- The feature-matched mintd suite passed 223/226 tests. Three unrelated
  environment-variable tests raced over process-global state; each passed when
  rerun in isolation with one test thread. A run without
  `federation-test-utils` also demonstrated the existing intended production
  rejection of four trusted-dealer startup fixtures.
- Repository-owned affected crates pass scoped rustfmt and `git diff --check`.

## Milestone 4 — proof-bound swap and melt conflict keys

**Status:** Deferred — requires a versioned journal migration

**Findings covered**

- SEC-2026-07-17-06
- Swap/melt conflict detection does not bind the operation to the complete set
  of input proof `Y` values.

**Review questions**

- Which operation variants consume proofs and therefore require proof-set
  conflicts?
- Are proof sets canonicalized identically across members?
- Must the quote ID remain part of the melt key in addition to proof Ys?
- How do retransmission and replay semantics distinguish identical operations
  from conflicting ones?

**Reassessment**

- The finding remains correct as a pre-application resource-amplification
  issue. Swap has no conflict keys, and melt conflicts only by quote ID, so
  overlapping spends can consume ordering and application work.
- It is not a database double-spend: deterministic application persists proof
  state and output signatures transactionally, and the existing sliding-window
  regression proves every later spend loses without receiving signatures.
- Duplicate Ys inside one request are already rejected by both swap and melt
  pure admission before consensus.
- Conflict keys are not ephemeral. They are serialized in every
  `FederationJournalEntry`, checked for exact equality during replay and suffix
  verification, and stored in the SQL `federation_journal_conflict_keys`
  index.
- The current envelope version is `5`, with no discriminator for the conflict
  derivation scheme. Adding proof-Y keys in place would make existing version-5
  journal entries fail `JournalConflictKeysMismatch` on restart. Relaxing the
  equality check would let newly supplied version-5 catch-up entries claim the
  legacy weaker key set.

**Attempt history and rollback**

- A candidate added a shared `ProofSpend { y }` conflict key, sorted and
  deduplicated Ys, retained melt quote keys, and covered overlapping swaps,
  cross-quote melts, disjoint inputs, reordering, and replay.
- The candidate passed all 462 active `cdk-common` tests plus its integration
  and doc tests. It intentionally moved the mint sliding-window regression
  from application rejection to journal conflict rejection; after updating
  that assertion, all 143 mint federation tests passed.
- Compatibility review then proved that the same candidate invalidated durable
  version-5 journal metadata and its SQL conflict-key index. Because no safe
  discriminator or backfill existed, the entire candidate and its adjusted
  test were removed before this milestone commit.

**Required prerequisite**

This fix must ship with a versioned migration that:

1. introduces a new operation/conflict-derivation version for newly submitted
   swaps and melts;
2. permits historical version-5 envelopes only in authenticated replay and
   catch-up paths, while live admission accepts only the current version;
3. backfills proof-Y keys into both journal rows and
   `federation_journal_conflict_keys` transactionally for SQLite and Postgres;
4. defines checkpoint, suffix-verification, and mixed-version catch-up
   behavior; and
5. proves rollback/restart at every migration boundary.

**Proof required**

- [x] Current overlap and duplicate-input behavior was reproduced.
- [x] The proposed proof-Y semantics passed focused and affected-crate tests.
- [x] Existing application-level transactional double-spend protection passed.
- [x] The incompatible candidate was fully rolled back.
- [ ] Versioned journal and SQL migration proof — deferred prerequisite.

**Decision**

Do not trade restart/catch-up integrity for a warning-severity DoS hardening
patch. The finding remains open for the next operation-format migration; no
production code from the failed candidate remains in this milestone.

## Milestone 5 — accepted-entry capability for threshold signing

**Status:** Kept

**Findings covered**

- CLEAN-005
- P18
- A public raw member signing API can sign arbitrary operation/output tuples
  without a type-level proof that consensus accepted the request.

**Review questions**

- Enumerate every call site and decide whether it possesses an accepted journal
  entry or equivalent durable capability.
- Can visibility alone close the boundary across the `cdk-common`/`cdk` crate
  split?
- What minimum fields must an unforgeable-in-process accepted-signing token
  bind?

**Reassessment**

- No current HTTP signing bypass was found. Production mint and swap handlers
  submit through consensus and retrieve persisted member shares; melt signing
  is reached from accepted-entry application.
- The boundary was nevertheless too permissive:
  `MemberConfigPrivate::sign_blinded_messages` was public and accepted an
  arbitrary operation ID plus arbitrary outputs. Test connectors used that
  surface directly, proving that code outside the application path could
  acquire it.
- Visibility alone cannot span `cdk-common` and `cdk`, and a journal entry is a
  serializable DTO needed by storage and catch-up. The useful enforceable
  boundary is therefore a typed request with private fields that can only be
  constructed after validating a complete journal entry and its operation.
- Mint and swap bind the complete ordered output vector. Melt needs a narrower
  rule because accepted change outputs may use zero-amount placeholders:
  signing may use only the ordered prefix, with exact blinded secret and keyset,
  and may replace only a zero placeholder with the deterministically assigned
  amount.
- A keyset ID binds the aggregate key generation, but an accepted request must
  also remain bound to the entire effective federation configuration. Otherwise
  a request could be validated under one rotation view and signed under another.

**Kept implementation**

- Added `FederationAcceptedSigningRequest` with private operation ID, accepted
  index, consensus evidence, effective-config digest, and ordered blinded
  outputs.
- Its constructor rejects rejected entries, an operation ID inconsistent with
  the canonical envelope, non-signing operation kinds, and output vectors not
  authorized by the accepted mint, swap, or melt operation.
- The signer recomputes the effective config digest before using the capability,
  then retains the existing federation-ID, signer-ID, BLS key kind, v3 keyset,
  amount, secret-share, public-share, and self-verification checks.
- The arbitrary tuple primitive is now private to the signing module. All
  production mint, swap, and melt application paths pass the accepted journal
  entry, and durable share provenance is created from that same entry.
- Existing fixture connectors now build accepted operations instead of using a
  magic operation ID. Public Axum handlers remain on consensus-submission and
  persisted-share-response APIs.

**Proof required**

- [x] Compile/API-boundary proof that ordinary request handling cannot
  invoke threshold signing directly.
- [x] Operation ID, output index, blinded message, amount, keyset, generation,
  and accepted entry are bound.
- [x] Existing accepted issuance/melt/swap paths still sign successfully.
- [x] Replay returns the same deterministic result without reauthorizing a
  different output.

**Attempt history**

- The first compile exposed that test-only direct share producers and expected
  response builders also relied on arbitrary signing. They were migrated to
  accepted mint/swap entries; the raw method was not re-exposed.
- The first Axum conversion incorrectly passed compact catch-up projections,
  which deliberately omit the envelope. That did not compile. The attempt was
  corrected to use the locally persisted full journal entries after catch-up.
- The initial capability bound the keyset but not the complete rotation view.
  Before acceptance, it was strengthened with the effective config digest and
  a changed-config rejection test.
- No failed production candidate remains.

**Validation evidence**

- `cargo test -p cdk-common --features federation signing --lib`: 18 passed,
  including rejected-entry, operation-ID mutation, output mutation,
  unsupported-operation, config-change, and deterministic replay cases.
- Accepted mint/swap runtime tests: 2 passed.
- Rotated-keyset melt signing and local sliding-window rejection regressions:
  2 passed.
- Four affected Axum apply/catch-up/result tests pass with
  `--features federation-bark`; the Axum test target compiles completely in that
  feature configuration.
- `cdk-cli` test binaries compile with
  `--no-default-features --features federation`.
- The full CDK library run reached 789 passing tests. Its only three failures
  were unrelated wallet-repository listener tests denied permission by the
  sandbox; every federation, mint-application, and wallet-connector test in
  that run passed.
- Repository-owned affected sources pass scoped rustfmt.

## Milestone 6 — remove secp/BLS enum panic surfaces

**Status:** Kept

**Findings covered**

- CLEAN-003
- Core `PublicKey` and `SecretKey` enums can contain BLS keys while secp-only
  methods contain panic paths.
- The BLS dependency/type surface is not consistently feature-scoped.

**Review questions**

- Inventory all public secp-only APIs and downstream call sites.
- Determine whether changing return types would be a semver-breaking public API
  change.
- Determine whether feature-gating serialized key variants would break stored
  data or protocol decoding.
- Prefer removing panics without creating silent algorithm confusion.

**Reassessment**

- All eight reported methods still panicked when a BLS variant reached a
  secp256k1-only operation. The mixed enum already had fallible BLS/secp
  accessors, so these panics were inconsistent rather than unavoidable.
- BLS base points and scalars cannot be gated behind `cashu/federation`.
  Standalone NUT-01 v3 blind signatures use the same BLS types; only threshold
  share construction belongs behind the federation feature. Gating the
  variants, parsers, or dependencies would make valid v3 keys and proofs
  undecodable in standalone builds.
- Keeping the old infallible signatures under deprecation would leave the
  reported panic surface live. The crate is still pre-1.0, so an explicit
  source-level API correction is preferable to preserving a critical
  algorithm-confusion footgun.
- Public-key wire encoding is unambiguous by compressed length and already
  round-tripped both algorithms. Generic `SecretKey` serde was not: it emitted
  the same 32-byte/hex shape for BLS and secp and always decoded it as secp.
  Therefore no valid generic BLS serde round trip existed to preserve.

**Kept implementation**

- Changed `PublicKey::to_uncompressed_bytes`, `x_only_public_key`,
  `x_only_public_key_with_parity`, and `negate` to return
  `Result<_, nut01::Error>` and `WrongKeyKind` for BLS variants.
- Changed the corresponding secret-key `x_only_public_key`, `to_scalar`,
  `as_scalar`, and `negate` methods to the same fail-closed contract.
- Made `dhke::hash_e` fallible and propagated kind failures through DLEQ,
  NUT-10, NUT-11, NUT-12, NUT-28, wallet send/receive/signing, and CLI receive
  paths. No caller substitutes compressed bytes or a BLS scalar into a secp
  algorithm.
- Preserved the exact existing human-readable and binary serde representation
  for secp secret keys. New BLS secret-key serde uses an explicit `bls:` text
  tag and a one-byte binary discriminator, so it round-trips without being
  silently reclassified as secp.
- Kept BLS base types and dependencies available without federation; threshold
  BLS APIs remain feature-scoped as before.

**Public compatibility impact**

- This is an intentional source-breaking change for callers of the eight
  formerly infallible methods and `dhke::hash_e`: callers must handle or
  propagate `WrongKeyKind`.
- Public-key, Cashu proof, DLEQ, and secp secret-key wire encodings are
  unchanged. Existing persisted secp values require no migration.
- Historical generic BLS `SecretKey` serde values cannot be migrated
  losslessly because their encoding carried no algorithm tag and old readers
  interpreted them as secp. New tagged values correct that defect without
  changing valid historical secp data.

**Proof required**

- [x] No non-test secp-only operation can panic on a BLS variant.
- [x] BLS and secp serialization round trips remain compatible.
- [x] Default and federation feature matrices compile.
- [x] Public API compatibility impact is documented.
- [x] Cashu and CDK crypto tests pass.

**Validation evidence**

- New unit tests exercise all eight BLS wrong-kind branches and secp/BLS
  public-key JSON plus secret-key JSON/CBOR round trips.
- `cargo test -p cashu`: 573 passed, 2 ignored; 11 doctests passed.
- `cargo test -p cashu --features federation nuts::nut01 --lib`: 31 passed,
  including all threshold BLS tests.
- `cargo check -p cashu --no-default-features` and the same check with
  `--features federation` pass.

## Milestone 9 — readiness and AlephBFT fairness

**Status:** Deferred

**Findings covered**

- P13 / A2: payment-observation submission bypasses the normal public readiness
  gate.
- R3: retry traffic can starve under continuous fresh traffic because retries
  are serviced only when no fresh messages are drained.
- DB-006: global ingress limits do not guarantee per-member fairness.

**Reassessment**

- The payment-observation submission method does bypass
  `ensure_federation_ready_for_public_submit`, but it is also the internal
  recovery path used by quote observers. Existing tests require it to record
  terminal payment evidence while the node is `AwaitingQuorum`. A blanket
  public readiness gate would therefore prevent the evidence needed to leave
  that state. The service needs an explicit policy that distinguishes
  authenticated internal recovery submissions from public/direct submissions
  and defines `Halted`, stale-generation, `CatchingUp`, `Lagging`, and
  `AwaitingQuorum` behavior.
- Retry starvation is real: the pump drains retries only on a tick that drains
  no fresh work. Two bounded weighted candidates were tried. Both preserved
  unit-level queue invariants, but synchronous retry delivery consumed enough
  head-of-line time to violate the existing wallet publisher-fallback latency
  bound (approximately 17–18 seconds versus the required maximum of 10
  seconds). A safe fix needs independently bounded/concurrent retry delivery
  rather than a scheduling ratio alone.
- The ingress route authenticates a sender before queueing, but
  `FederationAlephBftNetworkMessageEnvelope` and the queue accounting do not
  retain that identity. The existing byte and message caps are global.
  Reclaimable per-member fairness therefore requires a sender-aware envelope,
  admission accounting, and matching release accounting; an equal hard
  partition would unnecessarily strand global capacity when members are idle.

**Attempt history and rollback**

- A blanket observation-readiness candidate and focused rejection tests
  initially passed. The wider recovery tests then proved the policy wrong:
  mint and melt observers must persist terminal observations while sync is not
  ready. The candidate and its tests were removed, and both existing
  `*_records_observation_while_sync_not_ready` regressions pass again.
- A 1:1 fresh/retry scheduler, followed by an 8:1 weighted variant, passed the
  focused AlephBFT network test slice after excluding retries created during
  the same tick. Both failed the established wallet publisher-fallback latency
  acceptance test. All production and test changes from both variants were
  removed.
- No per-member quota candidate was installed because identity is discarded
  at the queue boundary; implementing only a partial counter would not prove
  isolation or correct capacity release.

**Deferred boundary**

- Define a submission-origin/readiness state machine before changing payment
  observation admission.
- Redesign retries as independently deadline-bounded or concurrent deliveries
  with a proven global in-flight cap and cancellation behavior.
- Carry authenticated sender identity through ingress queue ownership before
  adding reclaimable per-member message/byte budgets.

**Proof required**

- [ ] Halted/stale-generation states reject observations safely — deferred
  pending the submission-origin/readiness policy.
- [x] Intended recovery states continue to accept observations in the retained
  implementation.
- [ ] Retries make bounded progress under continuous fresh load — deferred
  pending non-blocking/concurrent retry design.
- [ ] One peer cannot consume every inbound slot/byte — deferred pending
  sender-aware queue ownership.
- [ ] Honest peers can progress while a peer floods to its quota — same
  prerequisite.
- [x] Existing global memory/channel bounds remain enforced and unchanged.
- [x] Failed candidates were completely rolled back and the affected recovery
  regressions pass.

**Validation evidence**

- `post_batch_check_mint_quote_records_observation_while_sync_not_ready` and
  `get_check_melt_custom_quote_records_observation_while_sync_not_ready` pass
  after the readiness candidate rollback.
- The 11-test AlephBFT network slice passed for the weighted scheduler's local
  invariants, but
  `federation_wallet_submit_operation_publisher_fallbacks_without_consensus_ordering`
  failed its latency bound for both scheduling ratios; this is rejection
  evidence, not proof of a retained fix.
- The wider Axum run also encountered sandbox-denied listener binds and a deep
  AlephBFT test stack overflow. Those environment/test-run limitations do not
  alter the candidate-specific failure above.
- The milestone leaves no source or test diff. Remaining items are live
  liveness/resource-isolation debt and must not be represented as fixed.

## Milestone 15 — wallet federation decomposition and common fanout

**Status:** Kept for exact policy-neutral cleanup; Rejected for broad
decomposition

**Findings covered**

- Cleanup/refactor plan phase 2
- The wallet federation module combines connector implementation, fanout,
  aggregation, validation, metrics, quote visibility, and orchestration.
- Retry and aggregation semantics have drifted across operations.

**Reassessment**

- The principal phase-2 correctness finding, `get_mint_keyset` aborting on one
  bad member and bypassing timeout/retry/concurrency policy, was already fixed
  and proven in Milestone 7. It uses `collect_member_results`, and malformed,
  stalled, conflicting, and below-threshold regressions remain green.
- The connector does not have one interchangeable fanout policy. Current calls
  fall into five materially different families:

  | Family | Current users | Completion/evidence rule |
  |---|---|---|
  | first healthy | DNS/LNURL proxy and quote creation | ordered fallback; a definitive rejection stops |
  | member discovery | mint info plus active keysets | both calls validate against the imported config and populate a cache |
  | threshold-equal | quote status, check-state, restore metadata | a matching value group must reach threshold |
  | threshold shares | mint, swap, melt change, restore | metadata and each member share are verified before aggregation |

  two sequential calls with an independent timeout for each, caches every
  immediately completed valid peer, and may stop before starting surplus
  members. Moving it to the common collector would apply one combined deadline,
  change retry behavior, and start the full roster before early return. It is
  not a behavior-neutral duplicate. Its normal and early-drain branches did,
  however, duplicate the exact response-validation/cache mutation body.
- Mint and melt quote creation have different request/response types and
  validation requirements, including optional melt quote IDs. A generic
  create/verify function would make those checks implicit and produce complex
  future/lifetime bounds. Only their retry loop is semantically identical and
  worth sharing.
- Renaming the public
  `FederatedMintConnectorConfig::mint_quote_visibility_*` fields or removing
  the public `FederationWalletConnector` facade is source-breaking. No API
  compatibility authority was supplied, so both proposals are rejected.
- Moving hundreds of aggregation and connector lines between files offers no
  runtime or correctness improvement by itself. As the module still has strong
  private coupling through response views, caches, and validators, the proposed
  full split would create a broad visibility diff similar to the rejected
  Milestone 14 module move. It is not worth doing in this cleanup.
- Performance tracing was the one genuine inverted dependency: standalone
  wallet verification imported federation internals and disappeared entirely
  without the federation feature. The hook is observation-only (`tracing` plus
  a unit return) and belongs in an always-built wallet performance module.
- The original in-memory melt-change recovery limitation is superseded by
  Milestone 2. A rebuilt connector now strips unverifiable change, while the
  wallet saga restores it using durable blinded outputs.

**Kept implementation**

- Extracted `record_member_active_keyset_result`, so normal completion and the

**Status:** Kept for exact invariant and typed-boundary cleanup; Rejected for

- DKG reconciliation remains coupled to builder/setup code.

- Prove which validation invariants are identical across modes and which are

**Reassessment**

- The plan was stale about the runtime discriminator: `FederationMode` already

  fund-sensitive change with no newly identified invariant.
- NUT-02 federation keyset publication/restart consistency was fixed and proven

  deferred there; it is not a second cleanup candidate.
- DKG startup reconciliation remains in the builder because it consumes
  durable records before mint construction. Moving it into a lifecycle service
  would change startup ownership without reducing a runtime dependency. The
  real defect was that incomplete evidence was detected by matching human
  error strings.

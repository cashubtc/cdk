02 Naming trap

"v3" means Version02.

Three names for the same thing — and one collision. Say this first or lose the room.

We sayRust enumID prefixMeaning
v1KeySetVersion::Version0000 + 7 bytesoriginal secp256k1 IDs
v2KeySetVersion::Version0101 + 32 bytessecp IDs committing to unit / fee / expiry
v3KeySetVersion::Version0202 + 32 bytesBLS12-381 keysets

Second collision

Cashu already has TokenV3 / ProofV3. Those are token encoding versions — nothing to do with BLS keyset v3.

Proto off-by-one

The signatory proto maps 1→v1, 2→v2, 3→v3 — off by one from the on-wire version byte. On original bls the proto still only named V1/V2 while the Rust enum already understood 3.

03 Why BLS before federation

You can't split a secp key and keep one public key.

Standalone Cashu is secp256k1 additive DHKE. Fine for one operator — but a wallet can't verify an ordinary proof against one mint key while k is shared. BLS12-381 swaps the algebra for a multiplicative pairing scheme.

secp256k1 · v1/v2 · additive

Y = hash_to_curve(secret)
B_ = Y + r·G
C_ = k · B_
C = C_ − r·K
prove k via DLEQ

No threshold issuance: splitting k across members breaks verification against a single public key.

BLS12-381 · v3 · pairing

B = r · H(secret) ∈ G1
C_ = k · B
C = r⁻¹ · C_
e(C, G2) == e(H(secret), K)
e(C_, G2) == e(B, K)

Mint keys live in G2 (96 B), messages & signatures in G1 (48 B). The pairing is what later lets t shares reconstruct one signature under one aggregate key — no DLEQ needed.

Scope limit

Original bls is single-signer. It does not implement threshold shares, Lagrange interpolation, DKG, federation keyset gates, member rosters, or consensus. Hash-to-curve DST: CASHU_BLS12_381_G1_XMD:SHA-256_SSWU_RO_.

04 Keyset v3 transition

The protocol switch is a keyset version, not a token format.

Default mint policy

use_keyset_v2: Some(false)→v1, Some(true)→v2, None→new keysets are v3. Live secp keysets stay active until explicitly rotated — upgrading the binary never rotates a live keyset. Rotation takes an explicit version: rotate-next-keyset --keyset-version v3.

05 Crypto building blocks

One PublicKey, three curves. Parse by length.

PublicKey — length-dispatched enum

Secp256k1 — 33 B compressed
BlsG1 — 48 B · blinded messages & signatures
BlsG2 — 96 B · mint public keys

Identity / infinity rejected on parse. BLS scalars are big-endian on the wire, reversed into bls12_381::Scalar. SecretKey::public_key() for BLS returns k · G2.

Hash-to-curve

secp keeps the old Secp256k1_HashToCurve_Cashu_ try-and-increment loop. v3 uses standard hash-to-curve: BlsG1PublicKey::hash_to_curve with ExpandMsgXmd<Sha256>. hash_to_curve_for_version() is the switch inside Proof::y().

DHKE entry points — everything branches on version

blind_message_for_version · construct_proofs · sign_message · verify_bls_message · verify_bls_blind_signature · verify_bls_message_keyed · batch_verify_bls_messages

NUT-12 DLEQ returns None for Version02; a v3 proof carrying DLEQ data fails construction. DLEQ stays secp-only.

Batch verification — NUT-00 transcript

prefix Cashu_BLS_Batch_v1
item: C ‖ K ‖ u32BE(len) ‖ msg
challenge = SHA256(transcript)
hᵢ = SHA256(challenge ‖ u32BE(i) ‖ u32BE(ctr))
rejection-sample canonical non-zero Fr*

The first cut reduced bytes with a one-byte counter and failed the published NUT-00 vector — fixed in 5d4d0d7ac. (A later federation-era Cashu_BLS_Blind_Batch_v1 is not part of original bls.)

06 Deterministic derivation

Rejection sampling everywhere. Never reduce raw bytes.

Wallet side — NUT-13

secret v2/v3: HMAC-SHA256 KDF
"Cashu_KDF_HMAC_SHA256" ‖ keyset_id ‖ u64BE(counter) ‖ 0x00
r (v3) same KDF, suffix 0x01, then attempt loop:
for attempt in 0..=u32::MAX:
    h = HMAC-SHA256(seed, msg ‖ u32BE(attempt))
    reject all-zero
    accept if h is a canonical BLS scalar

PreMintSecrets::from_seed and blank change call blind_message_for_version() — restore automatically follows the keyset's curve.

Mint side — NUT-02 MintKeySet::generate

v3 amount-key derivation evolved in three commits:

  1. feat: bls — BIP32 child bytes → SHA-256 → reduce into Fr
  2. 1d71add6e — drop the extra hash; reduce child bytes directly
  3. 59a7a80e5 — rejection-sample a second hardened index until the 32 child bytes are a canonical non-zero scalar
for amount index i:
    attempt = 0
    loop:
        child = BIP32(i' / attempt')
        reject all-zero
        accept SecretKey::bls_from_slice(child)

A unit test proves the live key is the rejection-sampled two-level child. Ephemeral blinding uses SecretKey::generate_bls() — the same Fr* sampler over OsRng.

07 End-to-end v3 proof life cycle

The walk that makes federation obvious.

The public wire protocol doesn't change. What changes is the algebra at each station — and a two-stage verification on the wallet.

No DLEQ on v3

If a v3 blind signature or proof carries DLEQ data, reject it. DLEQ is not defined for this curve in NUT-12 — pairings replaced it.

The fix that made it real — 289fe9e44

Early wallets could construct a v3 proof and skip the blind pairing check. verify_bls_blind_signature() is now wired into mint-response validation, restore, auth-wallet mint, and verify_token_signatures. A regression test asserts v3 tokens never encode "d": null DLEQ.

08 Mixed-curve safety

Making the old SDK safe for new points.

Once a public key can be secp, G1 or G2, old assumptions break. A compressed G1 point is valid hex and parses fine — so an attacker can smuggle BLS points into NUT-10 spending conditions.

The panic surface (original-branch leftover)

to_uncompressed_bytes · x_only_public_key · negate · to_scalar / as_scalar

P2PK / HTLC stay secp-only. Before 2dedc3ca7, a BLS point in nut10 data panicked inside x_only_public_key(); after, it returns NonSecp256k1Pubkey.

Rejections that matter

identity points on G1/G2 parse · zero scalars for blinding factors, mint keys, batch weights · non-canonical scalars in every sampler · NUT-00 batch vector pinned as a unit test in nut01/bls.rs

fuzz_bls_pubkey_in_conditions

Random hex almost never decodes to a subgroup-correct BLS point, so the fuzzer injects valid compressed G1/G2 points into P2PK/HTLC data, pubkeys, refund_keys — and asserts an error, never a panic.

fuzz_bls_dhke

Panic-safety across G1/G2/scalar parsing, blind / sign / unblind / verify and batch-weight sampling — plus soundness: honest v3 proofs verify, tampered ones fail.

Why this chapter exists

Federation multiplies every one of these paths by n members. The mixed-curve hardening is what the threshold code stands on.

09 Design fork

"Why not t-of-n secp signatures, like bare multisig?"

It would have prototyped. It would have been a worse Cashu federation — because the coin is the signature. BLS is the interpolated-secret design on a pairing curve, not multisig with nicer bytes.

The honest summary

Naive secp multisig federates the token. BLS threshold federates the issuer, then emits a normal token. Cashu cares about the second thing — the bearer object should stay boring.

What multisig got right

Blindness works, t-of-n availability works, and the expensive parts — consensus, replay, catch-up, payment observation — don't disappear either way. (And "why not FROST-sign the secret?" is a third design: a threshold Schnorr scheme that is no longer Cashu.)

Bitcoin can afford bare multisig because the coin lives in a UTXO that names its script. Cashu can't — the coin is the signature.

10 The threshold scheme we actually use

Classic Shamir, applied to a blinded G1 point.

One secret k per denomination, shared as k_i = f(i) under a degree-(t−1) polynomial. Any t shares interpolate C = k·B. Fewer learn nothing. Signer IDs are non-zero — interpolation happens at x = 0.

Share check

e(C_i, G2) == e(B, K_i)

Aggregate (any t of n)

C = Σ λᵢ(0)·C_i = f(0)·B = k·B

Then it's standalone v3

e(C, G2) == e(H(secret), K) · proof = r⁻¹·C

Not bare multisig (shares never reach the token), not FROST (that's the secp treasury scheme), not IETF aggregate-BLS (every share is of the same k·B). The in-tree 3-of-5 test shows subsets {1,3,5} and {2,3,4} reconstructing the same point with real scalars. A 1-of-1 keyset is a normal single-signer BLS key. Code: nut01/bls.rs — blind_sign_share() / aggregate_blind_signature_shares().

11 Threshold-signing mix-and-match

The sliding-window attack.

Every BLS share is independently valid — even if nobody else signed the same B. If members sign whatever they're shown, a wallet pays for 2 tokens and walks out with 3.

Not a BLS-math bug

This is what happens when a threshold issuer signs before it agrees on the exact message. The same trick works on swap: keep the inputs fixed, slide the output set. The milestone-12 suite uses four overlapping 3-output windows — ABC / BCD / CDA / DAB — against one 3-token quote.

What stops it

Hash the exact envelope into an operation_id. Same bytes, same ID; different output set, different ID. Members sign only the operation that consensus accepted. Shares carry the accepted operation_id. Signing threshold below consensus threshold is safe only because of this ordering.

12 Consensus before signing

Agree on the transaction before any signature exists.

Treat AlephBFT as a black box: envelopes in, one total order out. A member doesn't sign because it received an HTTP request — it signs because that exact envelope came out of the box as accepted.

An envelope is a name

envelope = { federation, kind: Swap, inputs: [P1,P2], outputs: [A,B] }
operation_id = hash(envelope)

Apply does the Cashu part

Verify proofs, mark inputs spent, sign accepted outputs. Replay is idempotent; a different output set for spent inputs → TokenAlreadySpent, no shares.

Mint vs swap lock

Mint/melt conflict on the quote ID. Swap locks via the inputs themselves: the first accepted swap spends them, the second window can't collect shares.

13 Data flow and transport

Two networks, same members.

The public plane is wallet→mint fan-out. The private plane is member↔member agreement. HTTP and Iroh are just two pipes for the same two planes — iroh://… is not a new protocol.

Public — fan-out

Same ordinary Cashu request to every member's public_mint_url. Liveness is the signature threshold: slow or offline members are ignored, bad shares dropped. The wallet is the aggregator — members never send shares to each other.

Private — /federation/v1

Member-authenticated. Carries consensus (envelopes, AlephBFT messages, journal catch-up) and later DKG. Wallets are not on this plane.

Quote creation is the exception

First healthy member creates it; the wallet then waits until a threshold can see it. Status polls fan out — never trust one member's "paid" or "issued". Code: crates/cdk/src/wallet/federation.rs.

14 BLS DKG — dealer-free key generation

Nobody ever holds k.

Dealer-free Pedersen DKG on the private member plane. Every member contributes a secret polynomial; the joint mint key is the sum of the constant terms. Once per denomination. Trusted-dealer setup is the same end state — used in tests.

Joint secret

f(x) = Σ fⱼ(x) · k = f(0)
k_i = Σ fⱼ(i) — never sees another polynomial

Verifiable delivery

fⱼ(i)·G2 == eval of j's public commitments at i — a lie is visible

Aggregate key

K = Σ Cⱼ[0] = k·G2
hash-commit first, so the last member can't adapt

Then transcript + member signatures, and only then activation — nobody signs eCash with the keyset before that. Wallets never see the dance: they see one ordinary v3 keyset. Code: crates/cdk-common/src/federation/dkg.rs.

15 Open challenge — client spend intent

Consensus can't stop the member who saw your proofs.

Audit SEC-2026-07-17-01. A proof is a bearer instrument: whoever presents (secret, C) can spend it. Today the envelope is authorized as "a member said so", not "the owner wanted these outputs".

What this is not

Not a BLS bug (the shares are valid — for the wrong outputs). Not mix-and-match (only one operation wins; it's the attacker's). Not solved by fan-out (fan-out is how the member learns the proofs). Not solved by DKG (DKG protects k, not bearer secrets).

The Cashu-shaped fix

NUT-11 SIG_ALL: lock the proof to P2PK and sign all outputs. Mutating A,B into X,Y invalidates the witness and changes the operation ID. Code can bind SIG_ALL today but doesn't require it — until it does, one receiving member stays trusted not to steal.

16 Funding backends — the other half of the mint

Don't build a committee that prints IOUs against one person's piggy bank.

A mint is two machines: the eCash issuer (BLS federation) and the funding backend where real money sits. Federating only the first leaves a king.

Federated BDK — on-chain treasury

No member loads a mnemonic. Members watch the chain, agree on addresses and unsigned transactions through the same consensus box, then jointly sign. One member can propose — it cannot move coins.

Federated Bark — Lightning treasury

Mint invoices and melt payments are consensus operations first. Claiming an HTLC or sending a payment is a threshold custody action, not "member 3's CLN paid it".

One classical node = one king

Point every member at a single CLN/LND/BDK and that operator can mark unpaid quotes paid, refuse or redirect melts, or sweep the funds while the eCash ledger looks honest. Voting can't stop a key they don't share.

The blunt rule

Same roster, same consensus history, and a treasury signing threshold no weaker than the eCash threshold. The quorum that issues must be the quorum that moves the reserves. Both backends use FROST on secp256k1 — a different key on a different curve for a different job. development_single_observation and fakewallet exist for tests; they are not a funding model.

17 FROST DKG

Two ceremonies, one roster.

Startup runs two dealer-free ceremonies under the same roster, ceremony ID and signature threshold. Both must finish; a partial result never makes the mint ready. The secrets never mix.

The FROST ceremony

frost-secp256k1-tr 3.0.0 in cdk-frost, ciphersuite secp256k1_sha256_tr_v1. Three rounds on the private plane: broadcast commitments → confidential per-recipient packages → root confirmation where every member publishes the same public package. Every message binds federation ID, ceremony, epoch, protocol, ciphersuite, threshold, roster, sender, receiver. Persist-before-send; a second different payload is equivocation.

What comes out

One untweaked, application-neutral root P; each member holds a sealed share s_i (AES-256-GCM at rest). Apps derive later, in exact order: root → domain tweak → chain code → non-hardened BIP32 → BIP340 even-Y → BIP341 key-path tweak. Bark and BDK are consumers — no second DKG. Any t members later emit an ordinary Schnorr signature; the private key is never reconstructed.

18 BDK mint and melt, step by step

Two public calls. Everything safe happens on the private plane.

Mint — checks that matter

Address allocation is consensus-owned (quote + epoch + keychain + index; replay reveals that exact index). Mempool is not payment — deposits need the observation quorum and confirmation depth. A reorg before issuance unsays the UTXO; after issuance it raises an alarm and does not unmint. Issuance still requires the paid quote and the exact output set.

Melt — checks that matter

make_payment creates an intent, not a payment. TransactionProposal carries the exact unsigned tx — every member recomputes ownership, value conservation, fee caps, destinations and sighashes. FROST authorizations bind operation + tx + input index + sighash; nonces burn on failure, never reuse. Signed bytes persist (TransactionSigned) before any BroadcastIntent. One member can't redirect the payout, sign a different tx, or broadcast alternate bytes.

19 Swap, step by step

The purest federated operation. No Bitcoin involved.

Ordinary POST /swap on the outside; consensus-before-signing on the inside. One envelope, one winner, shares only after accept.

What honest consensus gives

Only one exact input/output set gets signed. Inputs spend once across the roster. Shares exist only after accept, bound to operation_id, member, keyset, amount, output index. Replay is idempotent; restore returns those same shares, never new ones. Offline members catch up and serve the accepted shares — they cannot invent another window.

Admission rejects, before consensus

Empty inputs · duplicate inputs/outputs · non-v3 outputs · oversized proofs/witnesses · unbalanced amounts. Lagging members fail closed and return no shares. Unless proofs carry SIG_ALL, a Byzantine member who saw the bearer proofs can still rewrite and race — that's section 15, not a missing swap step.

20 Consensus messages on the wire

Named facts, ordered once.

AlephBFT orders FederationConsensusItems, not raw HTTP. An envelope's hash is its operation_id: same bytes, same ID; exact retries join; a different payload is a different operation.

Value operations

MintQuote · Mint · MeltQuote · Melt · Swap — one exact Cashu request, one envelope, one winner.

Observations & custody

MintQuotePayment · MeltQuotePayment · ChainObservation::{Deposit,Reorg} · TxBroadcast — one envelope per observer. AddressAllocation · TransactionProposal · TransactionSigned · BroadcastIntent.

Off-log by design

Wallet HTTP bodies · BLS shares · FROST packages · DKG messages · peer status / catch-up. For n members: C = n − ⌊(n−1)/3⌋, T ≤ C, observation Q ≥ C in production.

21 Roster and federation config

The roster is the constitution.

FederationId is SHA-256 over a domain-separated transcript: setup authorization, thresholds, and every member's ID, both URLs, and identity key. Change any byte and you haven't updated a federation — you've founded a new one. Try it:

Frozen — imply a new federation

add/remove/replace a member · rotate an identity key · change T or C · change payment-observation policy · change Bitcoin network / FROST epoch · change wallet protocol version · swap HTTPS↔Iroh or merge the two URLs · edit a DNS name that's in the roster. The only consensus mutation of the public signing surface is KeysetRotation.

Still open before "done"

22 Crash resistance, backup, catch-up

Peers can give you the book. Only your backup gives you the pen.

The book is the journal, checkpoints, certificates, catch-up. The pen is identity, BLS shares, the sealed FROST root. There is no BIP39 that regenerates a member seat.

Mechanisms that make it safe

Deterministic journal replay (same operation_id → same state and shares) · order digest + materialized-state digest bound by catch-up certificates · scheduled checkpoints as restart trust roots · checkpoint-bound DB restore with a manifest and no bypass flag · readiness gates — a half-restored node does not sign · persist-before-send / persist-before-broadcast · nonce lifecycle vacant→reserved→published→consumed · materialized-state audit latch with no force-clear.

Secrets lost?

Stop. Do not copy another member's private config — wrong seat, activation fails. The remaining members keep serving until you run a new setup with a new roster. Store snapshot + manifest + secret files together, as one generation.

23 Closing

The threshold lives in issuance.
The token stays boring.

The story in five lines

  1. BLS v3 swaps secp DHKE for pairings — one public key, verifiable without k.
  2. Shamir splits k; any t shares interpolate one ordinary signature.
  3. Consensus orders the exact envelope before anyone signs — killing mix-and-match.
  4. Dual DKG: BLS for eCash, FROST for the treasury. Same roster, same threshold.
  5. The roster is frozen law. SIG_ALL is the remaining hole.

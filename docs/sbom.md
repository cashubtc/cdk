# Software bills of materials

CDK collects CycloneDX 1.6 JSON documents for Rust **and** the dependencies of
its Dart, Swift, Go and Kotlin bindings. A Cargo inventory alone is not a binding
SBOM. Each run has separate ecosystem documents, resolved-dependency evidence
and an `index.json` associating the results. Documents are deliberately not
flattened: platform variants, build-only components and package identities must
not disappear during deduplication.

## Prerequisites

```sh
nix develop .#sbom
```

`flake.lock` pins the generators and their dependencies: cargo-cyclonedx,
cdxgen, CycloneDX CLI, Syft and cargo-auditable. The Gradle init script pins the
CycloneDX Gradle plugin to 2.4.1. The shell also supplies Python (3.11+), Cargo,
Dart, Go and JDK 17. Tools on PATH can be used without Nix; their versions are
recorded in the index.

Swift additionally needs the Swift toolchain and, for Apple artifacts, Xcode on
macOS. Kotlin collection needs an Android SDK compatible with the project (API
34), configured through `ANDROID_HOME`. Nix's `kotlin-publish` shell supplies
that SDK. The SBOM shell does not accept Android licenses or install Xcode.
Package resolution needs network access and any private-registry authentication
normally required by the package managers. Only run collectors on trusted code:
Cargo, Gradle and Swift manifests can execute code.

## Dependency inventories

```sh
just sbom cdk-mintd
just sbom cdk
just sbom cdk --no-default-features --features wallet
just sbom cdk-common --no-default-features --features wallet
just sbom cdk-ffi
just sbom rust # Explicitly collect only Rust, for every workspace member
just sbom dart
just sbom kotlin
just sbom cdk --target wasm32-unknown-unknown --no-default-features --features wallet
```

Every Rust workspace member is supported, discovered through Cargo rather than a
hard-coded crate list. `fuzz/` is excluded because it is not a workspace member.
Use qualified Cargo features when collecting multiple crates.

Go's release `go.mod` and Swift's release `Package.swift` are generated by their
publishing workflows; this checkout is **not** their assembled release package.
Pass the assembled package, with its actual manifests, generated sources and
binary targets, rather than inventing an empty substitute:

```sh
just sbom go --project go=/path/to/cdk-go
just sbom swift --project swift=/path/to/cdk-swift
just sbom bindings --project go=/path/to/cdk-go --project swift=/path/to/cdk-swift
# The default includes all crates AND all four language ecosystems:
just sbom --project go=/path/to/cdk-go --project swift=/path/to/cdk-swift
# Explicitly omit Swift when no Apple toolchain is available:
just sbom --exclude-language swift --project go=/path/to/cdk-go
```

To assemble a real local Go package from the pinned binding generator (not a
dependency fixture):

```sh
result=$(nix build .#go-bindings --no-link --print-out-paths)
just sbom-go-package --bindings "$result/bindings/cdkffi" \
  --library "x86_64-unknown-linux-gnu=$result/lib/libcdk_ffi_go.so" \
  --output target/sbom-go-package
just sbom go --project go=target/sbom-go-package
```

Supply one `--library TARGET=PATH` for **each** platform actually shipped. The
helper copies real generated code and libraries into the same module layout as
the Go release workflow; it never fabricates native code or overwrites a package.
It defaults to the v0/v1 module path; use `--module` for a different/v2+ path.

`--project dart=PATH` and `--project kotlin=PATH` can likewise select assembled
release projects. Collectors work on isolated copies, so package resolution and
generators cannot overwrite checkout lockfiles, generated SBOMs or manifests.

Collection includes:

| Ecosystem | Evidence and coverage |
|---|---|
| Rust | Root Cargo.lock, target-filtered Cargo metadata, single-package isolated consumer resolution, transitive inventory, separate scannable build-dependency document |
| Dart | `dart pub get`, complete `dart pub deps --json`, pubspec.lock, direct/transitive Pub packages (including development tooling) |
| Swift | Real Package.swift, SPM resolution and dependency tree, Package.resolved when present; no external dependencies is valid |
| Go | Actual go.mod/go.sum, selected-module list and `go list -deps -json ./...`; independently retains all selected modules and the resolved Go standard-library version; records cgo inputs and packaged native files; rejects replacements |
| Kotlin | Android release compile/runtime and JVM compile/runtime graphs, independently reconciled with generator output; separate project/settings buildscript/plugin dependency graphs; artifact hashes and native files inside resolved JARs/AARs |

Dart, Swift, Go and Kotlin documents are checked against the package managers' resolved
package lists so an apparently successful manifest-only scan cannot silently
drop transitive packages. Dart tooling is retained in the inventory; it is not
asserted to be shipped in the application's runtime. The Dart adapter preserves
Pub's authoritative dependency edges, because a lockfile-only scan loses them.
Go's full selected-module list is retained in a separate scannable
`bindings/go/selected-modules.cdx.json`, with every selected module required,
even when it is not imported by the product. The cdxgen document independently
requires all imported modules. Go
resolution uses the GOOS/GOARCH corresponding to the selected Rust target, with
cgo enabled. Unknown Go platform mappings fail rather than scanning the host.
Non-hosted Dart dependencies and Go module replacements currently fail with an
explicit unsupported-identity diagnostic rather than being mislabeled as
registry packages.

Rust procedural macros are compile-time tools even when declared in ordinary
`dependencies`. The Rust adapter follows runtime dependency edges without
crossing a build-dependency or proc-macro boundary. Macros, build dependencies
and packages reachable only through them remain in the inventory with
`cdk:rust:dependency-role=build` and `scope: excluded`: they are excluded from
runtime requirements, **not removed from the SBOM**. Dependencies also reachable
through a runtime path remain required. The embedded-artifact check only
requires runtime packages; an executable is not expected to contain its
compiler plugins or their dependencies.

Every Rust inventory also has a `<crate>.build.cdx.json` document. In that
document procedural macros, build dependencies and their transitive dependencies
have `scope: required`, including packages also used at runtime. Scan **both**
documents when checking advisories; a scanner that skips excluded components in
the main inventory must not hide build-tool vulnerabilities. Generation and
validation themselves are not vulnerability scans.

For one selected crate, a synthetic **resolution-only** consumer requests just
that crate's defaults/features. It is never compiled or included in the SBOM.
Every resolved dependency version/source/checksum must still match the original
Cargo.lock; only the synthetic root may be added to the consumer lock. Its
manifest, lock and metadata are retained. Workspace-wide inventories remain
workspace-resolved; use single-crate commands for specific consumer configurations.

Inventories describe a resolved package graph, **not** the exact contents of a
binary. Even isolated Cargo metadata may include dev-resolution feature
over-approximations. Build mode additionally records **all observed host/target
compilation units**, exact feature sets and a separate `<crate>.compiled.cdx.json`.
Source-only packages are not deleted from the source inventory. Embedded Rust
checks compare against the observed target compilation, not workspace-only
optional packages. Consumer applications can resolve different compatible
versions, and need their own SBOMs. Native C libraries are not fully identified
by Rust `*-sys` crate versions.

## Build-associated verification

```sh
just build-sbom cdk-mintd --target x86_64-unknown-linux-gnu --profile release
just build-sbom dart --profile release-ffi
just build-sbom cdk --no-default-features --features wallet --profile dev
just build-sbom cdk-common --no-default-features --features wallet --profile dev
```

This is intentionally stricter than inventory mode:

1. Collect the Rust and applicable language inventories.
2. Run `cargo auditable build --locked` for one package, with the same feature,
   profile and target settings recorded in the index.
3. Discover executables, shared libraries, static archives and Rust libraries
   from Cargo's JSON artifact messages; retain host/target compilation units.
4. Scan executables/shared libraries with Syft and require their embedded Rust
   inventory to cover observed target packages. Static/Rust libraries receive
   compilation/link-input inventories, **not** a claim of embedded verification.
5. Inspect actual target compilation/build-script messages, verify supported
   bundled native sources and link archives, and inventory ELF shared-library
   requirements from their installed-package provenance.
6. Inventory native build-time inputs and shared-library requirements of host
   build scripts/procedural macros separately from the target product.
7. Record artifact SHA-256 values and reject changes during collection. In build
   mode, supplied packaged native files must match verified artifact bytes or
   have explicitly supplied, reviewed artifact-bound native provenance.

The scannable toolchain document also identifies the compiler, installed target
Rust standard-library distribution and (for Android) NDK revision. Sysroot
archive hashes are retained as build-environment evidence; this is not a claim
that every installed sysroot archive is linked into the product.

`--artifact PATH` additionally requests verification of a final artifact. Automatic
native provenance currently requires the path reported by this Cargo build;
post-processing such as stripping needs its own provenance. A missing
audit section or unsupported executable format causes failure, **not** a fallback
to Cargo.lock. Both shared and static siblings are retained. Each artifact's
`verification` field distinguishes embedded verification from an observed
compilation/link-input inventory. An `rlib` or static archive is not a linked
deployment: final OS requirements still belong to its consuming executable.
Swift frameworks remain outside the tested platform coverage.

The command builds the Rust library/binary, not a complete Dart package or AAR.
Go build mode additionally compiles the assembled package and runs a native
load/call smoke test in private staging. It then checks that packaged library
hashes match the observed build (or reviewed external native evidence). A
different prebuilt library is **not** accepted merely because its name matches.
For Go, build the auditable Rust library first, assemble from those exact bytes,
then run `build-sbom go` with the same target/profile/features:

```sh
cargo auditable build --locked -p cdk-ffi-go --lib --profile dev --target x86_64-unknown-linux-gnu
just sbom-go-package --bindings "$result/bindings/cdkffi" \
  --library x86_64-unknown-linux-gnu=target/x86_64-unknown-linux-gnu/debug/libcdk_ffi_go.so \
  --output target/sbom-go-auditable
just build-sbom go --project go=target/sbom-go-auditable --profile dev
```

### Final package file inventories

Use `--distribution PATH` (repeatable) to inspect a final AAR/JAR/ZIP or assembled
directory. This includes native libraries nested in archives, compressed native
assets, WebAssembly and extensionless ELF executables. Native file paths,
formats, architecture and SHA-256 values are preserved; resolved Maven artifacts
also retain their owner coordinates and container hashes. Unrecognized native
formats, symlinks, unsafe ZIP paths and oversized/encrypted entries fail.

```sh
just sbom kotlin --distribution /path/to/cdk-android-release.aar
just sbom go --project go=/path/to/cdk-go --distribution /path/to/cdk-go
```

For build-associated verification of a multi-ABI AAR, provide the native
documents from the other ABI build runs as well as the current build:

```sh
just build-sbom kotlin --target aarch64-linux-android --profile dev \
  --project kotlin=/path/to/assembled/cdk-kotlin \
  --distribution /path/to/cdk-android-release.aar \
  --native-bom /path/to/verified-armv7-native.cdx.json \
  --native-bom /path/to/verified-x86-native.cdx.json \
  --native-bom /path/to/verified-x86_64-native.cdx.json
```

Each packaged native hash must match a built artifact or the exact artifact hash
in the supplied document; external evidence must identify a matching architecture.
For local byte-preserving package validation, a staged Android project can use
`android.packaging.jniLibs.keepDebugSymbols.add("**/*.so")`. This produces an
unstripped test package, **not** proof that the production stripping pipeline is
verified. Do not change production packaging merely to get a green SBOM check:
post-processed artifacts need their own provenance and final-byte verification.

**File coverage is not independent upstream-component provenance.** For example,
hashing JNA's native dispatch libraries and associating them with JNA's Maven
version does not establish the versions of every C library embedded within them.
Those versions still need upstream native provenance. Do not advertise a
file-inventory document as proving exhaustive embedded dependency identities.
Similarly, toolchain distribution versions do not independently resolve every
upstream component embedded in Rust's sysroot or the NDK's compiler runtimes.

### Native evidence

Static linking cannot reliably be reverse-engineered from a stripped binary.
The collector therefore does **not** guess native versions, treat the entire
Nix closure as shipped software, or equate `openssl-sys` with OpenSSL.

For an ordinary `build-sbom` build on Linux GNU targets (x86_64/aarch64) with
Nix-provenanced shared libraries,
native evidence is now generated automatically:

- Cargo JSON records include **cached** compiler artifacts and build scripts.
  Host and target outputs are distinguished. A `links` declaration alone is
  not evidence that a separate native library was linked.
- The bundled-source adapters cover SQLite, zstd, AWS-LC, libsecp256k1 and ring.
  They compare the cached `.crate` archive's SHA-256 to Cargo.lock, verify the
  unpacked files against that archive without extracting it, reject modified
  or extra source files, and hash the native archives selected by the build.
- SQLite, zstd, AWS-LC and libsecp256k1 versions come from their bundled upstream
  headers/build metadata, not the Rust wrapper version. Ring's C/assembly is
  identified by its actual ring source distribution; no fictional independent
  `ring_core` release is invented.
- Reviewed coordination-only declarations (such as rayon-core and the
  aws-lc-rs wrapper) are recorded with their verified Rust source provenance.
  Unknown declarations or changed/unexpected link flags still fail.
- Workspace-resolved packages that have no target compiler artifact are
  explicitly recorded as `resolved-only-not-compiled`; they remain in the
  resolved inventory, not falsely presented as native inputs to this binary.
- ELF `DT_NEEDED` dependencies are inspected using `readelf`, **not** `ldd` or
  execution of the binary. Nix package name/version metadata and exact shared
  library hashes identify the resolved inputs. Unresolved dependencies,
  unsupported search paths, unknown package provenance and changing inputs fail.
- Additional native search/link arguments or static-CRT overrides in Rust flags
  require further linker provenance instead of silently bypassing these checks.

Android native builds support the four Rust Android targets using an explicit,
API-qualified NDK linker from `ANDROID_NDK_HOME`. The `kotlin-build` shell supplies
these settings. Combine shells to obtain both SBOM tools and the NDK:

```sh
nix develop .#sbom --command nix develop .#kotlin-build --command \
  just build-sbom kotlin --target aarch64-linux-android --profile dev
```

Android `DT_NEEDED` platform libraries are checked against the NDK's platform
library metadata and exact API stubs. The SBOM records minimum API requirements,
NDK revision and stub hashes, **not** invented runtime bionic versions. Actual
platform libraries are provided by the deployment device. Non-platform shared
libraries still require explicit provider evidence. Only the reviewed 16-KB
page-alignment linker flags are accepted automatically, not arbitrary link flags.

Apple builds have a separate native adapter for the five existing macOS/iOS
Swift targets (including simulators). It inspects thin 64-bit Mach-O load commands
without executing the image, checks architecture/platform and the SDK recorded
in newly built images, and handles Cargo host build tools separately from target
outputs. Preflight selects Xcode's `xcrun` instead of requiring ELF tools for an
Apple-only build.

Public Apple framework and `/usr/lib` requirements must resolve to matching
TAPI v4/v5 stubs in the explicitly selected Xcode SDK. The evidence records SDK
version/build, settings and stub hashes, minimum OS and image SDK metadata.
Framework link flags require verified registry sources and no framework search
overrides. These are **OS-provided requirements, not bundled libraries**: SDK
versions, stub hashes and dylib compatibility versions do not identify deployed
OS library bytes or their independent upstream composition. Static archives
remain compilation/link-input inventories, not finalized downstream linkage.

Non-platform target dylibs and unclassified native flags still fail. Host
libraries from the selected Rust sysroot require exact file hashes and a unique
installed-component manifest; their distribution-file identity is explicitly
not an independent upstream LLVM identity. Universal images, inherited runpaths
and other host-library providers are not automatically supported. This Apple
path still needs actual GitHub macOS execution validation; Linux fixture tests
do not establish Apple runtime behavior.

The native document is bound to the artifact SHA-256 and target. Its companion
`evidence/native-provenance-*.json` records source, archive and shared-library
evidence. `evidence/cargo-build.json` preserves the relevant Cargo messages, not
arbitrary compiler diagnostics or build-script environment variables.
Known Cargo stripping-failure warnings fail collection even when Cargo reports
`build-finished: success=true`. The shared collector retains compiler diagnostics
in `evidence/cargo-build-failure.json` on build-record rejection.

These checks assume a trusted compiler, Cargo and build cache; they are **not**
a reproducible-build attestation or a defense against a compromised builder.
ELF resolution describes declared default paths, not runtime overrides or
`dlopen` plugins. Deployment/container SBOMs remain necessary. Unknown platforms
or native providers are not silently accepted.

For `--existing`, there is no observed build record, so provide
`--native-bom PATH` (repeatable) from the original build's reviewed native
provenance. That mode remains conservative and does not infer why a Cargo
`links` declaration was present. A supplied document must contain these metadata
properties:

```json
{
  "properties": [
    {"name": "cdk:artifact:sha256", "value": "<final artifact SHA-256>"},
    {"name": "cdk:target", "value": "x86_64-unknown-linux-gnu"}
  ]
}
```

For every applicable Cargo `links` value, include a component with the actual
native library version and a `cdk:rust:links` property, for example
`{"name": "cdk:rust:links", "value": "sqlite3"}`. A native document must have
the usual CycloneDX subject, components and dependency relationships; the
fragment above is only its metadata properties, not a complete document.

Obtain externally supplied versions from the actual target's bundled sources, Nix build inputs or
native build records, not the host's `openssl version`. This evidence is a
build-provenance assertion, not cryptographic proof of which C objects linked.
Any native dependencies without Cargo `links` declarations still require review.
The collector cannot automatically discover every such dependency.

Missing/mismatched evidence leaves an incomplete run with an actionable
diagnostic. Supplying evidence for one artifact cannot satisfy another
artifact's check. `--native-bom` is not a way to suppress failures in automatic
verification of a newly observed build.

## Output and failures

### Evidence assurances, not a single completeness claim

`status: complete` describes successful execution only. `index.json.assurance`
separately reports resolved dependencies, observed compilation, packaged-file
coverage, upstream native identities, final bytes, provenance authentication,
linker inputs and consumer execution. `overall` stays `partial` while embedded
upstream identities remain unresolved. Vendor-native blobs are listed by owner,
path and hash rather than silently disappearing behind a parent package version.

Use repeatable `--require-assurance DIMENSION` to fail a collection that does not
provide a requested guarantee. For example, an inventory-only command cannot
satisfy `compiled_packages`, and file hashes cannot satisfy
`upstream_native_identities`. Unauthenticated external native BOMs do not satisfy
`final_bytes`; use observed build indexes and the finalizer instead.

Relevant source files and build/collector definitions are hashed before
collection and checked again afterwards. A changing source tree fails the run.
`--clean-build` selects a new target directory inside the output without deleting
existing caches. This is a fresh output directory, **not** a hermetic compiler
cache audit or a reproducible-build claim.

`--linker-maps` observes the actual GNU/Android target linker, retains the raw map,
hashes named archive inputs and records contributed archive members. The map is
bound to the compiler-reported artifact bytes. LTO-generated contributions remain
in the raw map and are not misrepresented as a complete object-to-source graph.
Linker arguments are fingerprinted, not dumped with environment values. This
option may rebuild packages because Cargo sees a different linker wrapper.

### Actual post-processed release bytes

`finalize-sbom` verifies real stripped binaries or native files within final
packages, without disabling normal stripping:

```sh
just finalize-sbom --build-run /path/to/completed-build \
  --original /path/to/original/libcdk_ffi_go.so \
  --strip-tool strip --output target/sbom/stripped-go

just finalize-sbom --build-run /path/to/completed-build \
  --original /path/to/original/libcdk_ffi_go.so \
  --distribution /path/to/final/go-package \
  --go-project /path/to/assembled/go-package \
  --require-assurance final_bytes --require-assurance consumer_execution \
  --output target/sbom/final-go
```

The original must match an artifact in a complete, hash-validated build run.
Final native bytes must either match it exactly or preserve ELF identity,
complete file-backed segment content, program-header offsets/properties,
allocated sections and embedded Cargo audit metadata. Only the ELF header's
section-table location, section count and section-name-table index may change
inside mapped bytes; other mapped bytes (including section gaps) must match.
The final embedded Rust package set is scanned again and must
match. Runtime changes, missing evidence, changed audit metadata, misplaced JNI
ABIs and missing explicitly supplied artifacts fail. Static archives may match
exactly, but cannot use the ELF stripping-equivalence check.

`--strip-tool` runs the actual tool on private copies and records its identity,
arguments and before/after hashes. Existing distributions can instead be
checked after their real build system processes them; the tool does not invent
a command history for processing it did not observe. New native documents bind
the inherited component evidence to the final hashes and retain the originals.

For a four-ABI AAR, repeat `--build-run` and `--original` for all four native
builds. `--inventory-run` retains an independently collected final binding
project's language/build-tool inventories. Package manifests are checked for
changes during finalization. The release workflows now gate Android AAR staging
and Linux Go publishing on these final-byte checks; Apple/Windows Go verification
is not implied by a Linux gate. The Maven publication hook checks the AAR hash
again when the actual artifact is staged, rather than assuming an earlier
assembly remains unchanged.

### Signed builder provenance

```sh
just sbom-provenance target/sbom/completed-run \
  --signing-key /secure/operator-provisioned-ed25519.pem --builder ci-builder-id
just sbom-provenance target/sbom/completed-run --trust-policy /secure/policy.json \
  --require-assurance final_bytes --require-assurance authenticated_provenance
```

Signing uses OpenSSL Ed25519, produces a detached in-toto statement over the
exact index digest, and never copies private keys into output. The index binds
all documents and evidence. Signing is separate from trust: a generated signature
is not automatically trusted, and the unsigned index is not rewritten to claim
that it has authenticated itself. Verification produces an effective assurance
report with authentication added only after checking the operator's policy.
Keys must have restrictive permissions; encrypted keys/external KMS signers are
not implemented by this local-file signer.

The finalizer's `--trust-policy` authenticates every input build/inventory before
using it, but does not sign the resulting finalization. Sign that completed run
separately. Policies require authenticated inputs by default, so signing a
finalization built from unsigned assertions does not upgrade those inputs to
trusted evidence. `require_authenticated_inputs: false` is an explicit policy
relaxation, not the release default. Target permissions cover every artifact;
profile permissions also cover retained input build profiles. Optional
`max_age_seconds` constrains timezone-aware statement timestamps.

A policy explicitly authorizes public-key fingerprints, builder identities and
targets. Example (fingerprint is SHA-256 of the DER-encoded public key):

```json
{
  "version": 1,
  "require_clean_source": true,
  "require_authenticated_inputs": true,
  "profiles": ["release", "release-ffi", "final-artifact"],
  "keys": [{
    "public_key": "builder-public.pem",
    "sha256": "<64-character DER public-key SHA-256>",
    "builder": "ci-builder-id",
    "targets": ["x86_64-unknown-linux-gnu", "aarch64-unknown-linux-gnu"]
  }]
}
```

Private signing keys and production trust identities are **not configured by the
repository**. Release jobs remain visibly unsigned until operators integrate
their signer/policy. A signature authenticates a builder's evidence; it does not
prove a truthful builder, reproducibility or missing native component identities.

### Downstream execution tests

The finalizer's `--go-project` compiles a real importing executable against the
final native bytes and executes an offline native call. Dynamic-loader override
variables are cleared. Cross-target execution requires explicit `--go-runner`
and repeatable `--go-runner-arg` options; it is never reported as a host test.
Linux release matrix jobs perform this test on both native amd64 and arm64
runners. Local arm64 execution still requires a suitable runner/toolchain.

An opt-in Linux x86_64 SDK/emulator shell supplies a private Android consumer test:

```sh
nix develop .#sbom-android --command just test-sbom-android \
  --aar /path/to/final/cdk-android-release.aar --start-emulator \
  --output target/sbom/android-consumer
```

It compiles an actual app/test APK, checks that the CDK library in the APK matches
the final AAR bytes exactly, loads it through JNA and calls the generated API.
The test fixture preserves those already-finalized bytes, not the release
package's debug symbols. AVD data is confined to the new output directory, only
the spawned emulator is stopped, and physical devices are refused. An explicitly
selected `--serial emulator-N` is also supported. This shell downloads the pinned
SDK image under the repository's existing Android license configuration. Passing
one x86_64/API-34 test does not establish every ABI, API level or device.
If a recently stopped emulator's port is still reserved, choose another even
console port with `--port` rather than interrupting another emulator or ADB.

Default output is `target/sbom/<unique-run-id>/`. `--output PATH` selects a new
directory, and an existing directory is never overwritten. The output path is
printed on success.

```text
index.json
rust/<crate>.cdx.json
rust/<crate>.build.cdx.json
rust/<crate>.compiled.cdx.json
rust/<crate>.build-native.cdx.json
rust/<crate>.toolchain.cdx.json
bindings/<language>/...
packages/...
artifacts/...
evidence/...
```

The index distinguishes inventory and build-associated mode, requested scope,
Rust/binding coverage, Cargo `links` evidence coverage, source revision/dirty state,
tool versions, build configuration, document hashes and artifact associations.
`status: complete` means the **requested mode** completed, not that an inventory
was verified against a release. Limitations remain visible in every run.

All documents pass CycloneDX CLI schema validation and dependency-reference
checks. Evidence paths cannot overwrite each other, and all output hashes are
rechecked before a run is marked complete. Failed collections exit nonzero and, once output is created, retain an
`incomplete` index. Preflight failures do not create output. Staging files are
removed without deleting user files. No environment dump or authentication
configuration is included in evidence; resolved dependency metadata can contain
private package names and source paths, so review it before publication.

## Release use

Use inventory commands against the actual assembled binding project, after
generating manifests and before committing/publishing it. Generate one Rust
inventory per released target and feature combination, and retain all ecosystem
documents together. Do not label a host-target inventory as the SBOM for every
platform in an archive. Native versions need build-specific provenance as above.

Existing artifacts can be verified without rebuilding:

```sh
just build-sbom cdk-mintd --existing --target x86_64-unknown-linux-musl \
  --profile release-static --features postgres,prometheus,redis \
  --artifact /path/to/final/cdk-mintd --native-bom /path/to/native.cdx.json
```

The Android and Linux Go release jobs use observed builds and finalization as
described above. Other release targets are not silently labeled verified:
Swift static archives and other platform-native provenance need target-specific
evidence first. `--existing` checks embedded package versions
and supplied provenance, not a cryptographic attestation of the original build
command, profile or Nix derivation. Non-auditable binaries fail the check.

For Docker, additionally scan the **final image digest**, for example with
`syft scan IMAGE@sha256:DIGEST -o cyclonedx-json=container.cdx.json`. This covers
Alpine and certificates but cannot by itself reconstruct every statically
linked Rust/C dependency. Retain the binary's dependency documents alongside
the image document.

## Release-only SBOM builds and Apple diagnostics

`.github/workflows/apple-sbom.yml` is a **non-publishing diagnostic entry point**.
It runs only on `release: published` (including published prereleases), not on
pull requests, branch/tag pushes, schedules, manual dispatch or reusable calls.
It checks out the release event's exact commit, does not clone deployment
repositories, request signing keys, or publish packages. It calls the shared collector and uses the same Cargo
build-command helper as production collection; it is not a second SBOM builder.

The release job keeps the bounded `macos-arm64` matrix, `cdk-ffi-swift` product,
`release-ffi` profile and Xcode `16.4`, configured in workflow environment values.
Missing installations fail explicitly. Permissions remain read-only and the
workflow does not use deployment secrets.

Go and Kotlin SBOM builds remain inside their release-publishing workflows,
including nightly prerelease publishing; they have no standalone PR/push build
triggers. The lightweight offline SBOM regression tests still run in normal CI;
they do not generate release SBOMs or build release artifacts.

The workflow freezes the checked-out commit before creating its matrix, pins
Rust from `rust-toolchain.toml`, and gets SBOM tools and Protobuf (`protoc`) from
`flake.lock`. It uses
`macos-15` / `macos-15-intel`, not the retired macOS 14 image. Matrix concurrency
is capped at two jobs; release runs are grouped by tag and do not cancel earlier
runs, preserving their evidence.

Before entering Nix, the workflow resolves the pinned `cargo` and `rustc` with
`rustup which --toolchain`, records their binary directory and Cargo/rustup home
paths, and saves `rust-setup.log`. The launcher uses those explicit locations;
it does not assume that Rust is installed in `$HOME/.cargo/bin` or restore the
runner's entire ambient `PATH`.

The tools-only `sbom-apple-tools` Nix shell exports executable paths. The launcher
then selects Xcode and starts a clean native environment, dropping Nix SDK/compiler
flags, credentials and ambient loader overrides. It restores only the selected
Rust toolchain's `lib` directory in `DYLD_FALLBACK_LIBRARY_PATH`, matching the
runtime lookup bypassed by direct `rustup which` binaries, without substituting
Nix's LLVM or restoring arbitrary user library directories. A logged
`rust-objcopy --version` probe must succeed before inventory/build collection.
Rust builds use a fresh per-run target
directory. The diagnostic deployment minima are macOS 13 / iOS 14, matching the
Swift package; this is not an assertion about other products' compatibility.

**The first runs can legitimately fail.** The shared collector now selects its
Apple native adapter rather than treating missing `readelf` as an exemption.
Unknown providers, unsupported layouts and tool failures must remain red.
If the collector cannot reach compilation, a probe using its
shared Cargo invocation collects actual build records, archive member listings,
Mach-O load commands and embedded-Rust scans where applicable. It never converts
a failed verifier into successful release evidence or retries a failed compiler.
Swift package assembly, final XCFramework verification, signing and downstream
consumer execution remain separate implementation milestones.

Download the `apple-sbom-<product>-<target>-<run>-<attempt>` artifact from the
Actions run and share it with the run URL. It retains:

- `runner.log`, `rust-setup.log` and `bootstrap.log`, including tool-setup failures;
- `run/report.json`, per-command logs/exit codes and diagnostic limitations;
- resolved inventories and incomplete verifier indexes, when available;
- reduced Cargo build records, artifact hashes and Apple inspection reports;
- `run/diagnostic-files.json`, hashes of retained feedback files.

Artifacts are uploaded even after failures, retained for 14 days, and exclude
the large compiler target directory. Job cancellation/timeouts can leave an
incomplete bundle; do not interpret missing reports as success. Logs can contain
source paths or private package names, so review them before sharing publicly.
`release_ready` stays false: collecting diagnostics is not a signed release SBOM.

Only workflow syntax, orchestration and fixtures can be validated on Linux.
Actual Apple-tool behavior must be confirmed by these GitHub macOS runs.
Existing publishing workflows are intentionally not gated on this unfinished
Apple verifier yet.

## Tests

```sh
just test-sbom
```

The standard-library tests use temporary fixtures and mocked generators. They
need no package downloads, SDKs or running mint. Real collection still requires
the generators and platform tools listed above.

Ed25519 tests use system OpenSSL when available. To additionally exercise the
publication hook with real local Maven staging (requires a cached Gradle wrapper
distribution and Java):

```sh
CDK_SBOM_REAL_GRADLE_TESTS=1 just test-sbom
```

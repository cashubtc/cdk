Unlocked

Compact summary of durable capabilities. Historical checkpoint detail now lives in Git history and the implementation plan instead of this dashboard.

Consensus and replay

Federation operations have canonical IDs, ordered journal entries, conflict keys, distinct order and materialized-state digests, signed catch-up certificates, quorum-certified catch-up, restart replay, and fail-closed lag handling. Finalized AlephBFT items are the sole replayable catch-up history; compact catch-up operation projections retain only order commitments, application status, and standard Cashu rejection metadata, and are checked against reconstructed journal entries before state application is trusted. Catch-up certificates are named consistently across protocol metadata, storage, readiness, metrics, CLI output, and operator tooling, and derive their count, last index, and range digest instead of storing duplicate wire and SQL fields.

Mint, swap, melt, restore

Mint quote/payment, issuance, swap, melt quote/payment, melt execution, restore, and check-state flows have federation-aware routes or wallet fanout with accepted-operation signing/apply boundaries and member-mode guards against direct standalone value paths.

Threshold BLS and keysets

Members sign with local BLS shares, wallets aggregate verified shares, federation keysets are v3/BLS-only, accepted share records are bound to matching journal operation IDs, and rotation keeps old proofs spendable while routing new outputs to active aggregate keysets.

Private REST federation

Member traffic uses signed private REST envelopes with roster authentication, status, catch-up, operation submission, payment observation, DKG, and AlephBFT network-message and activity routes. Effectful DKG mutations share one durable replay watermark, while status, catch-up, DKG readiness, activity, and network messages use independent bounded in-memory replay windows. Operation submission is idempotent through its canonical operation ID and durable pending/finalized records, so liveness traffic cannot advance DKG admission and REST sequence numbers are never mistaken for consensus order.

Durable storage

SQLite and Postgres paths persist journal rows, expose indexed operation-ID journal lookup with SQLite query-plan coverage, effectful DKG replay watermarks, catch-up certificates, signature shares, payment observations, DKG records, and public config snapshots. Persistence ownership is split into journal/runtime, post-consensus application, and DKG families, with matching SQL modules and one shared static row shape and decoder for complex journal and finalized-Aleph records. Runtime readiness is deliberately not persisted: healthy, lagging, catching-up, verification, mismatch, and halt states are derived in memory from live Aleph availability, journal position, and certificate evidence. Materialized-state equality remains available through signed status, redacted row fingerprints, and catch-up digest verification without a write-only checkpoint table. Setup-only DKG config snapshots may now be replaced by the matching finalized DKG config snapshot while arbitrary federation config conflicts still fail closed.

Wallet federation

Every active member exposes its finalized public federation config through unauthenticated GET /federation/v1/config. Wallet discovery tooling can join from any one member URL, fully validates the v3/BLS config, requires that URL to identify exactly one roster member, and cross-checks the member ID, federation ID, wallet protocol version, and config digest against GET /v1/info before trusting it. The connector also supports federation invites, filters compatible members through a dedicated validation module, and uses one bounded typed collector for mint, swap, melt, restore, quote-status, and check-state fanout. Endpoint policies retain ordinary Cashu errors, validate threshold shares or matching state views, and cancel outstanding requests as soon as success or an exact threshold rejection is established; one member, mixed errors, timeouts, and invalid shares cannot decide a consensus-dependent rejection. A wallet may prefer one quote coordinator for the first creation attempt, but that preference grants no status, recovery, mint-info, LNURL, or authentication authority: mint, batch-mint, and melt quote status always require threshold agreement. The CLI supports federation add --mint-url <member-url> as well as config-file and invite imports, persists only public federation metadata, activates the connector at startup, resolves tokens by local or member mint URL, and routes normal mint, send, receive, melt, restore, balance, mint-info, and check-state commands through the federation wallet path.

DKG and rotation path

Dealer-free setup is complete through independent member identity enrollment, public-only roster assembly, local roster binding, durable commitments, reveals, secret shares, transcript signatures, setup-only activation, final config assembly, restart/resume, conflict rejection, status inspection, and smoke helpers. Production builds exclude trusted-dealer tooling and reject trusted-dealer transcripts; the explicit test-utils feature preserves it only for local regtest. The signed Pedersen transcript remains an immutable historical attestation across later consensus key rotations.

Operations and tooling

Mintd can generate local federation configs, run smoke scripts, run repeated standard/long-partition smoke-operation batches, inspect configs, query signed status, compare digests, view payment observations, run DKG status checks, generate fresh fake invoices, and exercise SQLite/Postgres process flows. Detailed private member status now has one canonical wire DTO shared by Axum and mintd, with complete healthy, lagging, catching-up, verification, quarantine, alert, and halted-state coverage. Stable development Bash and TOML assets live as directly reviewable templates outside Rust; validated Rust generation still owns quoting, secrets, permissions, and exact fail-closed substitution. Scripted end-to-end CLI wallet smokes now run against live five-member threshold-three AlephBFT fakewallet federations and complete minting, swapping, receiving, token check-state, melting, copied-seed restore, balance, convergence checks, one-offline-member restart catch-up, and insufficient-threshold mint failure without proofs.

BFT adapter groundwork

The federation runtime is AlephBFT-only from startup and proposal admission through finalization, replay, and catch-up. Backend selectors, backend enums, the single-implementation consensus trait, the in-memory consensus engine, runtime dispatch, status labels, synchronous local append finality, the idle local finalization queue, obsolete mint-to-mint primary forwarding, and the second finalized-unit broadcast driver are gone. Upstream Aleph sessions are now the only source of finality; the private finalized-unit delivery route and DTOs have been removed. Peer and catch-up fixtures finalize actual Aleph adapter units and carry finalized-item evidence; direct journal tests stay at the narrower journal boundary. Every member submits directly to AlephBFT, while duplicate operation IDs are deduplicated under the consensus lock and share one response waiter. Signed private network messages, durable backups and pending proposals, activity-aware wakeups, session rotation, strict finalized-item replay, quorum-certified catch-up, equivocation rejection, unavailable-member recovery, and materialized-state verification remain covered.

Federation keyset safety

Federation startup, wallet discovery, minting, swapping, restoring, and melt change signing reject non-v3/non-BLS aggregate keysets while standalone legacy keysets remain unaffected. Federation mint-info carries typed federation ID, member ID, config digest, and one wallet protocol version, and wallets reject missing or mismatched member metadata before signing fanout. Internal operation, consensus-item, private-REST, Aleph-unit, and catch-up versions stay in their member-facing payloads and cannot make a compatible wallet reject public metadata. Federation mode is pre-deployment and v3/BLS-only, so old experimental federation keysets are kept only in negative tests; federation config and invite JSON reject a missing wallet protocol version, missing payment-observation policy, partial payment contexts, removed operator-limit fields, missing invite versions, and the old fake-wallet alias instead of defaulting them.

Recovery and convergence

Offline, lagging, restarted, and partially-applied members can replay accepted history, verify digests and quorum evidence, rebuild materialized mint state, catch up across paid melt observations without duplicate outgoing payments, and refuse public signing until healthy. Paid melts that crash between durable paid/spent state and terminal cleanup now resume the existing Finalizing saga from exact persisted settlement data, while failed-payment rollback remains all-or-nothing and replayable.

Liveness and resource bounds

The post-work CPU spin, history-scan, phase-dependent inactive-provider stall, and healed-partition pending-finalization stall are fixed. Active AlephBFT work uses a bounded 100ms cadence; replayed consensus-data gossip cannot refresh activity; cheap peer status uses maintained cursors and O(1) journal tips; and idle members no longer create an unbounded empty-unit DAG. A signed session- and operation-bound private REST activity wake releases held peer preunits when new work is admitted. While a durable operation remains pending, one representative lease renews halfway through the existing grace window; after finality clears pending rows the task blocks with no timer, database read, REST request, or unit wake. Dealer-free DKG is capped at 64 members and 64 denominations; its maximum supported signed reveal is 800,039 bytes under a 1 MiB route budget, CPU-heavy setup work remains semaphore-bounded, and one post-authentication slot per roster member prevents cross-member in-flight starvation. The partition regression now rebuilds restarted members through the same durable runtime replay as daemon startup and uses production activity pacing, avoiding an artificial fast-test round backlog. Operation admission remains bounded, catching-up members fail closed before value mutations, backup persistence retries transient storage contention, and wallet fanout tolerates slow, offline, rate-limited, pending-finalization, rejecting, and bad-share peers while threshold remains reachable.

Architecture Decisions

Fedimint as reference, CDK simplicity as constraint

Use Fedimint for invariants and patterns, but keep smaller CDK-native designs when they preserve the same safety properties.

Private REST first

REST is the MVP member transport because it fits existing CDK server/client patterns and is easy to test locally.

Consensus before signing

No member may return a usable blind signature share until the exact operation has been accepted by consensus.

AlephBFT-owned consensus runtime

Federation mode has one ordering implementation: upstream AlephBFT. Public routes submit canonical operations to that runtime, finalized units enter one durable apply path, and restart and catch-up reconstruct the same journal and finalized-item evidence without backend dispatch or an in-memory consensus substitute.

Simulate network faults before BFT

The early CDK-native simulator supplied deterministic delay, duplication, reordering, offline catch-up, and quorum-refusal coverage while AlephBFT was being integrated. It has now been removed along with its unused parallel adapter runtime after real AlephBFT fault, restart, catch-up, and process coverage superseded it.

Bounded consensus admission

Consensus items are canonicalized and size-checked before batching, and duplicate operation hashes are collapsed while they are still pending.

Upstream finalization delivery

The upstream AlephBFT session is the sole source of ordered finalized units. One durable apply-and-notify path persists finalized evidence, appends the journal, applies mint state, checkpoints the materialized digest, and releases operation waiters.

Direct AlephBFT integration

The runtime implements upstream AlephBFT data-provider, finalization-handler, network, keychain, hashing, spawning, and backup interfaces directly. Signed private REST carries opaque Aleph messages and authenticated activity wakes; SQL persists backup bytes, pending operations, finalized items, journal entries, and recovery cursors. Readiness follows the real live-session handle and inbound queue, while local status exposes queued, pending-finalization, finalized, and accepted counters. The former simulator, backend trait, preview/exact-drain protocol, synthetic finality mode, quorum-broadcast driver, and private finalized-unit delivery route have all been removed.

Digest format before DB wiring

Materialized state convergence starts with a backend-neutral row snapshot and deterministic hash before individual storage adapters are asked to enumerate their mint state rows.

Status digests are materialized

Private status and signed catch-up evidence fail closed if database rows cannot be read, and peers compare both accepted order and applied mint-state digests before reopening signing paths.

Federation keysets are v3/BLS-only

Aggregate federation keysets use Cashu keyset v3 IDs and BLS public keys exclusively; v1/v2 keysets remain standalone-only unless a future protocol explicitly adds support.

No old federation compatibility

Federation is still undeployed, so federation configs, invites, fixtures, route behavior, and keyset metadata are strict current-shape artifacts. There is no compatibility branch for old experimental federation behavior; operators should regenerate development configs rather than relying on silent defaults, implicit limits, old aliases, missing-version upgrades, or migration shims for experimental formats.

One consensus backend

The unused public in-memory multi-member simulator, parallel backend-adapter runtime, backend selector, local engine, and enum dispatch are gone. Config, environment variables, generated scripts, and recipes always use AlephBFT, including dealer-free DKG setup. Finalized-item cursors, immutable order digests, materialized-state digests, operation height, and quorum evidence remain the convergence checks, and Aleph recovery targets the production consensus runtime directly.

Restore is a threshold read

Restore has been removed from the consensus operation model because it neither signs new outputs nor mutates mint state. Healthy members read signature shares persisted by accepted mint, swap, or melt-change operations; lagging members fail closed, non-v3 placeholders are rejected before lookup, and the wallet requires matching threshold views before aggregating BLS shares. The no-op operation kind, envelope, replay branch, projection branch, and synthetic fixtures are gone. Full common, mint, wallet, standalone restore, and 423-test Axum federation suites pass, including live one-member-offline value windows.

One canonical request commitment

The unused request-transcript type and second hash have been deleted. Consensus, duplicate detection, conflicts, signing provenance, persistence, and catch-up use the domain-separated operation ID computed from the complete canonical envelope. Mutation tests still prove that NUT-20 outputs, witnesses, P2PK/HTLC data, and SIG_ALL output sets change the operation ID, while canonical key sorting and the golden vector remain stable.

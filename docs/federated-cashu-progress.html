Compact summary of durable capabilities. Historical checkpoint detail now lives in Git history and the implementation plan instead of this dashboard.

Consensus and replay

Federation operations have canonical IDs, ordered journal entries, conflict keys, state digests, signed session outcomes, quorum-certified catch-up, restart replay, and fail-closed lag handling.

Mint, swap, melt, restore

Mint quote/payment, issuance, swap, melt quote/payment, melt execution, restore, and check-state flows have federation-aware routes or wallet fanout with accepted-operation signing/apply boundaries and member-mode guards against direct standalone value paths.

Threshold BLS and keysets

Members sign with local BLS shares, wallets aggregate verified shares, federation keysets are v3/BLS-only, accepted share records are bound to matching journal operation IDs, and rotation keeps old proofs spendable while routing new outputs to active aggregate keysets.

Private REST federation

Member traffic uses signed private REST envelopes with roster authentication, sequence watermarks, status, catch-up, operation submission, payment observation, DKG, and AlephBFT finalized-unit routes.

Durable storage

SQLite and Postgres paths persist journal rows, expose indexed operation-ID journal lookup with SQLite query-plan coverage, sequence watermarks, session outcomes, signature shares, state-digest checkpoints, payment observations, DKG records, public config snapshots, and sync status.

Wallet federation

The wallet connector discovers federation invites, filters compatible members, fans out requests, handles retries, slow members, mixed final/pending/rejected responses, invalid share responses, and one offline member during key discovery, aggregates threshold-valid mint/swap/melt/restore shares, and requires threshold check-state agreement.

DKG and rotation path

Trusted-dealer setup is working, route-driven DKG setup is scaffolded through durable commitments, reveals, secret shares, transcript signatures, setup-only activation, status inspection, and smoke helpers.

Operations and tooling

Mintd can generate local federation configs, run smoke scripts, inspect configs, query signed status, compare digests, view payment observations, run DKG status checks, and exercise SQLite/Postgres process flows.

BFT adapter groundwork

The consensus runtime has a simulator-backed adapter and an AlephBFT adapter boundary with queueing, preview/drain, drained-unit pending tracking, peer-decided item cleanup, finalized-unit delivery, deterministic rejected finalized conflicts, response waiters, duplicate handling, post-admission duplicate replay, pending conflict-key rejection, and status counters including pending-finalization items.

Architecture Decisions

Fedimint as reference, CDK simplicity as constraint

Use Fedimint for invariants and patterns, but keep smaller CDK-native designs when they preserve the same safety properties.

Private REST first

REST is the MVP member transport because it fits existing CDK server/client patterns and is easy to test locally.

Consensus before signing

No member may return a usable blind signature share until the exact operation has been accepted by consensus.

Runtime-owned consensus engine

Server state depends on a small consensus runtime wrapper and trait surface, so the current in-memory ordering source can be replaced without rewriting public routes, storage replay, or catch-up handlers.

Simulate network faults before BFT

The CDK-native simulator gives deterministic coverage for message delay, duplication, reordering, offline catch-up, and quorum refusal before adding a heavier real consensus backend.

Bounded consensus admission

Consensus items are canonicalized and size-checked before batching, and duplicate operation hashes are collapsed while they are still pending.

Backend-owned finalization delivery

Federation submissions now deliver accepted entries through a queue-backed finalization task; the inline path remains for focused fixtures, while router-created state uses the same apply-and-notify boundary future consensus engines can target.

Adapter before BFT

The first backend adapter is simulator-backed and operation-focused, while the AlephBFT adapter runtime and Axum helper now expose explicit preview, quorum-broadcast, router-started bounded driver ticks, bounded remote finalized-unit delivery, queue-and-wait submit, duplicate pending waiter joining, semantic conflict-key rejection for queued and drained quote operations, deterministic rejected outcomes for finalized semantic conflicts, drained-unit pending-finalization accounting with peer-decided duplicate/conflict cleanup, typed retryable pending-finalization timeouts, bounded response waiters, bounded accepted-response cache retention, pending sequence handoff, pending-mempool admission backpressure, exact-drain, external-finalization calls, and signed local-status counters for queued, pending-finalization, finalized, and accepted work so future BFT wiring cannot mistake local admission for accepted consensus order or hide queued/finalized adapter state from operators.

Digest format before DB wiring

Materialized state convergence starts with a backend-neutral row snapshot and deterministic hash before individual storage adapters are asked to enumerate their mint state rows.

Status digests are materialized

Private status and signed catch-up evidence fail closed if database rows cannot be read, and peers compare both accepted order and applied mint-state digests before reopening signing paths.

Federation keysets are v3/BLS-only

Aggregate federation keysets use Cashu keyset v3 IDs and BLS public keys exclusively; v1/v2 keysets remain standalone-only unless a future protocol explicitly adds support.

Real payment observations fail closed

Fake-wallet testing keeps one-observation finality, while real-backend policies require a configured quorum, reject single-observation finality, and now have pure matching/conflicting observer evaluation ready for DB-backed persistence.

Feature-off compatibility

The first Rust scaffold is gated so normal standalone builds do not see federation mint fields or APIs.

Trusted-dealer first

Milestone 1 starts with local polynomial shares so later DKG work can reuse the same share verification and aggregation code.

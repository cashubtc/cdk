# Migration notes for v0.19

## Breaking changes to `cdk-sql-common` pooling and transactions

Downstream SQL backends using the public pooling and transaction APIs must
account for these source-breaking changes from v0.18. The built-in SQLite
and PostgreSQL backends already use the updated APIs.

### Construct transactions from pooled connections

`ConnectionWithTransaction::new` now accepts only `PooledResource<RM>`, where
`RM: DatabasePool + 'static`. It previously accepted any suitable
`Deref`/`DerefMut` wrapper around a connection, such as `Box<DB>`. Although
the transaction type remains generic, constructing it with an arbitrary
non-pooled wrapper is no longer supported.

Migrate custom backends by implementing `DatabasePool` for a manager whose
`Connection` is your database connector and whose `Config` implements
`DatabaseConfig`. Construct a `Pool` with that configuration, then pass the
resource returned by `get().await` directly to the transaction constructor:

```rust
use cdk_sql_common::database::ConnectionWithTransaction;
use cdk_sql_common::pool::Pool;

// MyPool is the downstream DatabasePool implementation; config is its Config.
let pool = Pool::<MyPool>::new(config);
let connection = pool.get().await?;
let transaction = ConnectionWithTransaction::new(connection).await?;
// Execute transaction work, then explicitly commit or roll back.
transaction.commit().await?;
```

The example assumes an async caller that handles both pool acquisition and
transaction errors. A backend needing a single connection can configure
`DatabaseConfig::max_size()` to return `1`. There is no public constructor
that adopts an existing standalone connection or another pool's wrapper.

The pooled resource supplies the existing stale flag to transaction cleanup.
Keeping that resource owned until rollback completes prevents reuse after
cancellation; failed or cancelled rollback marks it stale. Do not restore
the old construction order by awaiting `BEGIN` before creating the guard.

### Own pool configuration and connection data

`DatabasePool::Connection` and `DatabasePool::Config` now require `'static`.
The manager type also needs `DatabasePool + 'static` to call `Pool` methods.
Connection creation runs in a blocking task that may outlive the acquiring
future, so these types cannot borrow data with a shorter lifetime.

Replace borrowed configuration fields such as `&str` and `&Path` with owned
`String` and `PathBuf` values, or use `Arc<T>` for shared owned state. Likewise,
connections must own their handles and any state they retain rather than
borrow from the configuration passed to `new_resource`. Add `'static` to
generic manager bounds where needed. This bound does not require leaking
objects or keeping them alive forever; ordinary owned values satisfy it.

### Handle connection-construction task failures

`cdk_sql_common::pool::Error<E>` has a new public variant,
`Task(tokio::task::JoinError)`. Update exhaustive matches over `Poison`,
`Timeout`, and `Resource` to include `Task(join_error)`, propagating or mapping
the join error into your application's error type. It reports failure to join
the connection-construction task, such as a panic, rather than a database
error returned by `new_resource`; those errors still use `Resource(E)`.

## LND backend initialization

The LND backend now calls `GetInfo` during `Lnd::new` to cache the node pubkey
and invoice network. Initialization requires a reachable LND node and a
macaroon that permits `info:read` or the specific `/lnrpc.Lightning/GetInfo`
RPC. This applies whether self-payments are enabled or disabled.

The standard `admin.macaroon` already permits this call. Before upgrading,
update custom restricted macaroons to permit `GetInfo` in addition to their
existing permissions. Missing permission or invalid node information now
returns an initialization error before the backend accepts payments.

The cached information lets the backend reject invoices for another network
and disallowed self-payments locally. Existing paid or pending payments are
reconciled before dispatch validation. These checks prevent new rejected
payments from getting stuck; they do not resolve previously pending quotes.

## Wallet trait removal

The `cdk_common::wallet::Wallet` trait (often imported as `WalletTrait`) and
its implementations for the CDK and FFI wallets have been removed. Use the
inherent methods on `cdk::wallet::Wallet` or `cdk_ffi::wallet::Wallet` instead.
Remove trait imports and replace trait-qualified calls with inherent method
calls. Downstream generic bounds and custom implementations must migrate to
concrete wallet types or an application-owned trait.

The trait aliases `check_mint_quote`, `mint_unified`, and
`melt_human_readable` map to `check_mint_quote_status`, `mint`, and
`melt_human_readable_quote`, respectively. For FFI wallets, use the exported
method signatures and FFI types; for example, rate limiting is configured
through `set_rate_limit`. For native wallets, replace
`set_rate_limiting_config(None)` with `disable_rate_limiting()` and pass the
configuration directly to `set_rate_limiting_config` when enabling pacing.
The exported UniFFI API is unchanged.

# Migration notes for v0.19

## Wallet receive persistence

Receive accounting now requires the atomic `WalletDatabase::finalize_receive`
operation. Custom Rust databases and foreign-language database callbacks must
implement its proof, transaction, saga-version, and rollback contract. There is
no non-atomic fallback. Transaction upserts must preserve terminal statuses.
The built-in SQLite, PostgreSQL, Redb, and Supabase adapters implement this contract.

General seed restoration also requires `WalletDatabase::restore_proofs`.
Its validated batch, conditional receive-saga version advancement/provenance
invalidation, and proof lifecycle changes must commit atomically. Conflicts
return false without writes; existing proof states are never reset (a mint
Pending result can restrict Unspent), and previously
observed consumed identities must not be reinserted. There is no non-atomic
fallback. Custom foreign-language database callbacks must implement this method
too. Rebuild generated bindings with the updated callback interface.
The same transaction advances keyset counters past the restored derivation
indices, so an interrupted scan cannot make those indices available again.
It must also lock/compare the supplied keyset-counter snapshot and validate all
receive saga versions (including ProofsPending), before committing any changes.
The caller snapshots the counter before sagas and proof identities. Intervening
allocation or saga transitions must return false without writes, even when a new
receive has already completed and removed its saga.

Supabase operators must apply the new receive-finalization migrations before
upgrading clients. These migrations add the atomic receive and restoration RPCs and advance the required
schema version to 11; use the operator workflow in the
[Supabase migration guide](../../crates/cdk-supabase/migrations/README.md).
SQLite, PostgreSQL, and Redb need no schema changes for receive finalization.

`ReceiveOperationData` adds the serialized `atomic_settlement` provenance flag.
New receives set it before contacting the mint. Missing fields deserialize as
false, retaining conservative recovery for legacy receipts. Custom adapters must
round-trip this field; custom Rust struct literals must initialize it. This is
an additive JSON-record change, not a database schema migration.

Run startup recovery before initiating new wallet operations. Inconclusive
receive recovery remains pending for a later retry; applications must not treat
deferred recovery or a failed recovery attempt as a completed payment.

## LND backend initialization

The LND backend now calls `GetInfo` during `Lnd::new` to cache the node pubkey
and invoice network. Initialization requires a reachable LND node and a
macaroon that permits `info:read` or the specific `/lnrpc.Lightning/GetInfo`
RPC. This applies whether self-payments are enabled or disabled.

The standard `admin.macaroon` already permits this call. Before upgrading,
update custom restricted macaroons to permit `GetInfo` in addition to their
existing permissions. Missing permission or invalid node information now
returns an initialization error before the backend accepts payments.

The cached information lets the backend reject invoices for another network
and disallowed self-payments locally. Existing paid or pending payments are
reconciled before dispatch validation. These checks prevent new rejected
payments from getting stuck; they do not resolve previously pending quotes.

# Migration Guide: v0.18.x to v0.19.0

## Summary

**Three breaking changes to the `cashu` crate:**

1. **`Amount` no longer implements the arithmetic operators** → use
   `checked_*` or `saturating_*`
2. **`ProofsMethods::sum_by_keyset` returns `Result`** → add `?`
3. **`Amount::split` and `Amount::split_with_fee` have bounded failure modes**
   → handle two new error variants

**Key Changes:**
- `a + b` → `a.checked_add(b).ok_or(Error::AmountOverflow)?` or
  `a.saturating_add(b)`
- `proofs.sum_by_keyset()` → `proofs.sum_by_keyset()?`
- a mint-advertised input fee larger than the proofs it applies to now returns
  `Error::InsufficientFunds` instead of panicking

`Amount` implemented `Add`, `Sub`, `Mul` and `Div` as
`checked_*().expect(...)`, so every bare operator on a monetary value was a
panic, in release builds too, reachable from values a mint controls. Removing
the impls moves the decision to the call site: fail on overflow, or saturate,
but say which.

The LND backend also gained an initialization requirement, unrelated to the
arithmetic changes; see [LND Backend
Initialization](#lnd-backend-initialization).

## LND Backend Initialization

The LND backend now calls `GetInfo` during `Lnd::new` to cache the node pubkey
and invoice network. Initialization requires a reachable LND node and a
macaroon that permits `info:read` or the specific `/lnrpc.Lightning/GetInfo`
RPC. This applies whether self-payments are enabled or disabled.

The standard `admin.macaroon` already permits this call. Before upgrading,
update custom restricted macaroons to permit `GetInfo` in addition to their
existing permissions. Missing permission or invalid node information now
returns an initialization error before the backend accepts payments.

The cached information lets the backend reject invoices for another network
and disallowed self-payments locally. Existing paid or pending payments are
reconciled before dispatch validation. These checks prevent new rejected
payments from getting stuck; they do not resolve previously pending quotes.

## Quick Reference

| Operation | Before | After |
|-----------|--------|-------|
| **Add** | `a + b` | `a.checked_add(b).ok_or(Error::AmountOverflow)?` |
| **Add, saturating** | `a + b` | `a.saturating_add(b)` |
| **Add-assign** | `a += b` | `a = a.checked_add(b).ok_or(Error::AmountOverflow)?` |
| **Subtract** | `a - b` | `a.checked_sub(b).ok_or(Error::AmountOverflow)?` |
| **Subtract, clamped at zero** | `if a > b { a - b } else { Amount::ZERO }` | `a.saturating_sub(b)` |
| **Multiply** | `a * b` | `a.checked_mul(b).ok_or(Error::AmountOverflow)?` |
| **Divide** | `a / b` | `a.checked_div(b).ok_or(Error::AmountOverflow)?` |
| **Sum by keyset** | `let m = proofs.sum_by_keyset();` | `let m = proofs.sum_by_keyset()?;` |
| **Backend fee reserve** | `(percent * amount as f32) as u64` then `max` | `fee_reserve.for_amount(amount)` |

## Detailed Changes

### 1. Amount no longer implements the arithmetic operators

The removed impls are `Add`, `AddAssign`, `Sub`, `SubAssign`, `Mul` and `Div` on
`Amount` (that is, `Amount<()>`). The replacements were already on the type:

```rust
use cashu::amount::Error;
use cashu::Amount;

fn totals(a: Amount, b: Amount) -> Result<Amount, Error> {
    // Before: a + b, which panicked on overflow.
    let sum = a.checked_add(b).ok_or(Error::AmountOverflow)?;
    let diff = a.checked_sub(b).ok_or(Error::AmountOverflow)?;
    let prod = a.checked_mul(b).ok_or(Error::AmountOverflow)?;
    let quot = a.checked_div(b).ok_or(Error::AmountOverflow)?;

    println!("{sum} {diff} {prod} {quot}");
    sum.checked_add(diff).ok_or(Error::AmountOverflow)
}
```

All four return `Option`, and `checked_div` is `None` on a zero divisor as well
as on overflow, so a division no longer has to be guarded separately.

Where overflow is not a real possibility and an error would only be noise,
saturate explicitly:

```rust
use cashu::Amount;

fn running_total(credits: &[Amount], debits: &[Amount]) -> Amount {
    let mut running = Amount::ZERO;
    for credit in credits {
        running = running.saturating_add(*credit);
    }
    for debit in debits {
        running = running.saturating_sub(*debit);
    }
    running
}
```

`saturating_sub` replaces the `if a > b { a - b } else { Amount::ZERO }` dance
that a subtraction needed to avoid the panic. `Amount::ZERO` and `Amount::ONE`
are unchanged.

Choosing between them: use `checked_*` whenever the value reaches a user, a
mint, or the database, so an impossible total surfaces as an error rather than a
plausible wrong number. Saturate only for display and for already-bounded
tallies, and say so at the call site.

#### Amounts carrying a unit

`Amount<CurrencyUnit>` has its own pair, which also rejects a mismatched unit
and so returns `Result` rather than `Option`:

```rust
use cashu::nuts::CurrencyUnit;
use cashu::Amount;

fn add_sats() -> Result<Amount<CurrencyUnit>, cashu::amount::Error> {
    let a = Amount::new(10, CurrencyUnit::Sat);
    let b = Amount::new(3, CurrencyUnit::Sat);

    let _diff = a.checked_sub(&b)?;
    a.checked_add(&b)
}
```

Note these take the other operand by reference, and that adding a `Sat` amount
to a `Msat` one is `Error::UnitMismatch` rather than a silently wrong total.

### 2. ProofsMethods::sum_by_keyset returns Result

```rust
fn sum_by_keyset(&self) -> Result<HashMap<Id, Amount>, Error>;
```

The error is `cashu::nuts::nut00::Error`, the same type the neighbouring
`total_amount()` already returned, so a function that handles one needs nothing
new for the other:

```rust
use cashu::nuts::nut00::ProofsMethods;
use cashu::Proofs;

fn report(proofs: &Proofs) -> Result<(), cashu::nuts::nut00::Error> {
    // Before: let by_keyset = proofs.sum_by_keyset();
    let by_keyset = proofs.sum_by_keyset()?;
    let total = proofs.total_amount()?;

    for (id, amount) in by_keyset {
        println!("{id}: {amount} of {total}");
    }
    Ok(())
}
```

The `Err` arm is an overflow while summing, which previously panicked. If you
implement `ProofsMethods` yourself, update the signature in your impl.

### 3. split and split_with_fee are bounded

Both methods already returned `Result`; what is new is that inputs which used to
succeed can now fail.

`Amount::split` counts the parts before allocating and refuses to produce more
than `MAX_SPLIT_PARTS` (4096), returning `Error::SplitTooManyParts(value,
parts)`. Denominations come from the mint's keyset, so a keyset offering only
small denominations previously made a split allocate one element per
denomination unit. A power-of-two keyset never needs more than 64 parts, so no
ordinary split is affected.

`Amount::split_with_fee` steps toward a total that covers its own swap fee in a
loop bounded by `MAX_SPLIT_WITH_FEE_STEPS` (1024), instead of recursing once per
satoshi, and returns `Error::SplitWithFeeDidNotConverge(value)` when it runs
out of steps.

```rust
use cashu::amount::{Error, FeeAndAmounts, MAX_SPLIT_PARTS, MAX_SPLIT_WITH_FEE_STEPS};
use cashu::Amount;

fn split(amount: Amount, fee_and_amounts: &FeeAndAmounts) -> Result<(), Error> {
    match amount.split(fee_and_amounts) {
        Ok(parts) => println!("{} parts", parts.len()),
        Err(Error::SplitTooManyParts(value, parts)) => {
            println!("{value} needs {parts} parts, over the {MAX_SPLIT_PARTS} allowed");
        }
        Err(err) => return Err(err),
    }

    match amount.split_with_fee(fee_and_amounts) {
        Ok(parts) => println!("{} parts", parts.len()),
        Err(Error::SplitWithFeeDidNotConverge(value)) => {
            println!("{value} did not converge within {MAX_SPLIT_WITH_FEE_STEPS} steps");
        }
        Err(err) => return Err(err),
    }

    Ok(())
}
```

Both constants are public, so a caller can check an amount against the bound
before asking for the split.

### 4. Fee reserve moves to FeeReserve::for_amount

`FeeReserve::for_amount` is now the one place the reserve is computed, and
`cdk-cln`, `cdk-lnd` and `cdk-fake-wallet` all call it. If you maintain a
payment backend outside this repository, replace your own percentage math with
it:

```rust
use cdk_common::common::FeeReserve;

// Before, in each backend:
// let relative = (self.fee_reserve.percent_fee_reserve * amount.value() as f32) as u64;
// let absolute: u64 = self.fee_reserve.min_fee_reserve.into();
// let fee = max(relative, absolute);

// After:
let fee = self.fee_reserve.for_amount(amount);
```

This changes the numbers. The old form multiplied in `f32`, whose 24-bit
mantissa cannot hold a large amount, and truncated the product; `for_amount`
multiplies in `f64` and rounds up. At a 1% reserve, 21,000,000,000 computed
209,999,984 before and computes 209,999,996 now. A reserve can therefore be
slightly larger than on v0.18, and is correct rather than rounded down for large
amounts. The percentage itself is still stored as `f32` on `FeeReserve`, so a
reserve is still not exactly 1% of the amount; what is fixed is the precision
lost in the multiplication.

A negative `percent_fee_reserve` is clamped to zero, and a product that does not
fit a `u64` is clamped to `u64::MAX`, so the result is always at least
`min_fee_reserve`.

## Behavior Changes

No signatures change here, but what your code observes does.

### Proof selection reports insufficient funds instead of panicking

A mint can advertise an `input_fee_ppk` large enough that the fee on the
selected proofs exceeds their total value. `Wallet::select_proofs` previously
underflowed and panicked; it now returns `Error::InsufficientFunds`, and keeps
selecting when a larger proof is still available to cover the fee. A wallet that
caught nothing around selection because it could not fail should now handle that
error.

### LND amounts spent

`cdk-lnd` converts millisatoshi values with `try_from` rather than `as`, so a
negative value from the node can no longer read as an enormous amount spent. A
conversion that would have wrapped is now an error on that payment.

### FFI bindings

No caller changes. The bindings moved their internal arithmetic to
`saturating_*`; no exported signature and no returned value changed.

## Lint

`clippy::arithmetic_side_effects` is denied inside `cashu::amount` and nowhere
else. That module is where an amount is still a raw `u64`, so the lint stands in
for the operator impls the type no longer has. Everywhere else the compiler does
the work: with no `Add`, `Sub`, `Mul` or `Div` on `Amount`, bare arithmetic on a
monetary value does not build. Arithmetic on counters, indices and timestamps is
untouched and keeps using plain operators.

## Troubleshooting

### "cannot add `cashu::Amount` to `cashu::Amount`"

```
error[E0369]: cannot add `cashu::Amount` to `cashu::Amount`
```

**Cause:** the `Add` impl is gone. The same error appears as "cannot subtract",
"cannot multiply" and "cannot divide" for the other three.

**Fix:**
```rust
let sum = a.checked_add(b).ok_or(Error::AmountOverflow)?;
// or, where saturating is right:
let sum = a.saturating_add(b);
```

### "binary assignment operation `+=` cannot be applied to type `cashu::Amount`"

```
error[E0368]: binary assignment operation `+=` cannot be applied to type `cashu::Amount`
```

**Cause:** `AddAssign` and `SubAssign` are gone with the rest.

**Fix:** assign the result back.
```rust
running = running.checked_add(amount).ok_or(Error::AmountOverflow)?;
```

### "expected `HashMap<Id, Amount>`, found `Result<HashMap<Id, Amount>, Error>`"

**Cause:** `sum_by_keyset` returns `Result`.

**Fix:** add `?` in a function returning `nut00::Error`, or map the error.
```rust
let by_keyset = proofs.sum_by_keyset()?;
```

### A split that used to work now returns an error

**Cause:** `Error::SplitTooManyParts` means the keyset's denominations would
need more than `MAX_SPLIT_PARTS` elements for this amount.
`Error::SplitWithFeeDidNotConverge` means no total within
`MAX_SPLIT_WITH_FEE_STEPS` satoshis of the requested one covers its own swap
fee.

**Fix:** neither is retryable with the same inputs. Check the keyset's
denominations and the mint's `input_fee_ppk`, and report the failure rather than
looping.

### A melt reserves slightly more than before

**Cause:** `FeeReserve::for_amount` rounds up and no longer loses precision in
`f32`. See [Fee reserve moves to
FeeReserve::for_amount](#4-fee-reserve-moves-to-feereservefor_amount) for the
size of the difference.

**Fix:** none needed. Lower `percent_fee_reserve` if the new reserve is larger
than you want.

# Migration notes for v0.19

## LND backend initialization

The LND backend now calls `GetInfo` during `Lnd::new` to cache the node pubkey
and invoice network. Initialization requires a reachable LND node and a
macaroon that permits `info:read` or the specific `/lnrpc.Lightning/GetInfo`
RPC. This applies whether self-payments are enabled or disabled.

The standard `admin.macaroon` already permits this call. Before upgrading,
update custom restricted macaroons to permit `GetInfo` in addition to their
existing permissions. Missing permission or invalid node information now
returns an initialization error before the backend accepts payments.

The cached information lets the backend reject invoices for another network
and disallowed self-payments locally. Existing paid or pending payments are
reconciled before dispatch validation. These checks prevent new rejected
payments from getting stuck; they do not resolve previously pending quotes.

## Wallet trait removal

The `cdk_common::wallet::Wallet` trait (often imported as `WalletTrait`) and
its implementations for the CDK and FFI wallets have been removed. Use the
inherent methods on `cdk::wallet::Wallet` or `cdk_ffi::wallet::Wallet` instead.
Remove trait imports and replace trait-qualified calls with inherent method
calls. Downstream generic bounds and custom implementations must migrate to
concrete wallet types or an application-owned trait.

The trait aliases `check_mint_quote`, `mint_unified`, and
`melt_human_readable` map to `check_mint_quote_status`, `mint`, and
`melt_human_readable_quote`, respectively. For FFI wallets, use the exported
method signatures and FFI types; for example, rate limiting is configured
through `set_rate_limit`. For native wallets, replace
`set_rate_limiting_config(None)` with `disable_rate_limiting()` and pass the
configuration directly to `set_rate_limiting_config` when enabling pacing.
The exported UniFFI API is unchanged.

## `SecretKey` no longer dereferences to secp256k1

`cashu::SecretKey` no longer implements `Deref<Target = secp256k1::SecretKey>`.
Use the explicit methods instead: `as_secp256k1()` to borrow the inner key,
`secret_bytes()`, `as_scalar()`/`to_scalar()`, `x_only_public_key()`,
`mul_tweak()`, `add_tweak()` and `negate()`. The tweak methods and `negate()`
return a `cashu::SecretKey`, so drop any `.into()` after them.

## Payment request creation

`CreateRequestParams` adds optional `payment_id` and `nostr_pubkey` fields.
Rust callers using exhaustive struct literals must add these fields or use
`..Default::default()`. Set both to `None` to retain the previous behavior:
no request ID and an ephemeral receiving identity for Nostr transport.

Existing serialized FFI parameter records may omit the new fields. Generated
binding constructors default them to `None`/`nil`/`null`.

### Spending-condition validation

Request creation now reports errors instead of skipping malformed spending
keys or capping an oversized signature threshold. An explicitly empty key
list and simultaneous `hash` and `preimage` inputs also return errors.

Pass `pubkeys = None` when no signing keys are intended. When providing keys,
use a signature threshold from one through the number of keys, and supply at
most one of `hash` or `preimage`. These checks apply to Rust, CLI, and FFI
callers.

## BLS v3 keysets

CDK adds BLS12-381 keysets (keyset ID version byte `02`, called "v3" in
configuration). Proof signatures use G1 points and mint keys use G2 points; v3
signatures carry no DLEQ proof.

V3 keysets are experimental. They implement cashubtc/nuts#443 (keysets v3:
BLS12-381 signatures and nutroot secrets) at commit `d9928f0`, which is not
yet merged, so the wire format may still change.

### Nutroot secrets and transactions

A v3 secret is the lowercase hex of a compressed secp256k1 point, and `Y` is
hashed over its 33 decoded bytes. Spending conditions are committed into the
point (NUT-10 nutroot secrets: an internal key tweaked by a tree of condition
leaves); NUT-10 P2PK and HTLC secrets are pre-v3 only.

Every operation on v3 keysets is a transaction (NUT-00): each v3 input,
including the quote of a mint request, carries a witness signing its input
digest over the request's transcript. In particular:

- Minting onto a v3 keyset needs a locked quote; an unlocked one is refused
  with error `20009`. The witness binds the quote's `amount_issued`.
- The mint returns a v3 proof's witness and `input_digest` from check-state
  and `proof_state` notifications while it is pending or spent.
- Tokens carry each v3 proof's spend info (`spend_info` in JSON, `si` in V4
  tokens) and never its witness.
- v3 blind auth tokens sign the request they authorize: method, target and
  body hash. Requests with a `Content-Encoding` are refused.
- A NUT-18 payment request asks for v3 payments with its `nutroot` option
  (NUT-26 tag `0x0b`).

v3 keysets created before this release used a different secret derivation
and `Y` (cashubtc/nuts#371): rotate them, and redeem their proofs on the old
keyset first.

### DLEQ proofs and spent tracking

v3 signatures and proofs never carry a DLEQ proof (NUT-00). A CDK mint
rejects a v3 input that carries one, and a CDK wallet rejects a v3 blind
signature or received proof that carries one.

A proof's `Y` is computed on its keyset's curve, so spent state is tracked per
curve. A secret signed under both a secp256k1 keyset and a v3 keyset can be
spent once on each. Each proof needed its own paid blind signature, so this
does not create value.

### Mint operators

New keysets still default to v2 (Version01), and existing keysets are kept.
V3 is opt-in because wallets without BLS support cannot use v3 keysets:

- `cdk-mintd`: set `keyset_version = "v3"` under `[info]`, or
  `CDK_MINTD_KEYSET_VERSION=v3`. It accepts `v1`, `v2` and `v3`, takes
  precedence over `use_keyset_v2`, and rotates an active keyset of a different
  version on startup.
- `cdk-mint-cli rotate-next-keyset --keyset-version v3` rotates a single unit.
  Omitting both version flags still selects v2.
- Library users: `MintBuilder::with_keyset_version(Some(KeySetVersion::Version02))`.

V3 keysets need the mint's NUT-06 identity `pubkey` (`mint_info.pubkey`,
`MintBuilder::with_pubkey`): wallets derive v3 quote lock keys from it. The
builder and keyset rotation refuse a v3 keyset without it. Once the mint has
a v3 keyset its info lists the core nutroot leaves under `nuts.10.leaves`.

V3 keyset units must match `[a-z0-9_-]+`. Existing v1 and v2 keysets keep
their previous unit rules.

The signatory gRPC schema version is now 4, and peers using an older schema
are rejected. Upgrade a remote signatory and the mints that use it together.

Fake-wallet `keyset_rotations` entries accept `version = "v3"`; the default
remains `v1`.

### Wallet database

Wallet SQLite and PostgreSQL databases run migration `20261116000000`, which
widens the `transaction_ys` length check to accept 48-byte BLS proof
identifiers. Existing rows are preserved. Redb is unchanged.

They also run `20261119000000`, which adds a nullable `spend_info` column to
`proof`. Supabase wallets apply the matching migrations and require schema
version 11. Redb stores spend info within each proof's JSON.

### Mint database

Mint SQLite and PostgreSQL databases run migration `20261119000000`, which
adds a nullable `input_digest` column to `proof`.

### Wallet behaviour

- New mint quotes on a mint with an identity pubkey are locked with NUT-13
  type `0x04` keys under a per-mint quote counter; BIP32 NUT-20 keys remain
  for mints without one and stay recoverable.
- Receiving a v3 proof runs the NUT-00 receive checks. By default an `after`
  leaf must open at least an hour away (`ReceiveOptions::v3_min_refund_horizon`)
  and `threshold` or `hashlock` leaves are refused, unless the proof pays the
  payee's own request (`ReceiveOptions::v3_payment_request`).
- Requested script-only (NUMS) payments are swept through a satisfiable
  disclosed leaf, using `ReceiveOptions::p2pk_signing_keys` and, for hashlocks,
  a 32-byte hex preimage in `ReceiveOptions::preimages`. Leaf keys tagged for
  blinding are derived from the proof's ephemeral key and NUT-28 slot map.
  An `after` leaf must already be open to sweep through it.
- For automatic Nostr receipt, attach receiver or leaf keys and preimages with
  `NostrWaitInfo::with_receive_options` before calling
  `WalletRepository::wait_for_nostr_payment`. The wait info retains the original
  Nutroot request for the payee checks. Both methods are available through FFI.
- `cdk-cli receive --payment-request <CREQ>` checks a v3 payment against the
  original CREQ-A or CREQ-B request's nutroot tree. Supply the leaf or receiver
  signing keys with `--signing-key` and hashlock preimages with `--preimage`.

### Rust API changes

- `PublicKey` and `SecretKey` remain secp256k1-only for P2PK, Nostr and other
  secp256k1 identity/signing roles. Existing secp256k1-only code does not need
  curve checks, and `PublicKey::to_bytes()` still returns `[u8; 33]`.
- Blind-signature protocol points (`B_`, `C_` and proof `Y` values) use
  `DhkePoint`, whose variants are secp256k1 and BLS12-381 G1.
- Mint denomination keys use `MintPublicKey`, whose variants are secp256k1 and
  BLS12-381 G2. `Keys` and `MintKeyPair::public_key` now expose this type.
- Blinding scalars use `BlindingFactor`, while mint signing scalars use
  `MintSecretKey`. Both support secp256k1 and BLS12-381, and require an explicit
  `as_secp256k1()` or `as_bls()` conversion before curve-specific operations.
- `DhkePoint::to_bytes()` and `MintPublicKey::to_bytes()` return `Vec<u8>`.
  `MintPublicKey::from_slice` and `from_hex` accept only mint-key encodings.
- `DhkePoint` no longer has `from_slice`, `from_hex`, `FromStr` or
  `Deserialize`, because a point's curve is set by its keyset. Parse external
  input with `from_slice_for_version` or `from_hex_for_version` and the
  keyset's `KeySetVersion`. `from_slice_any_curve` and `from_hex_any_curve`
  choose the curve from the encoding length and are meant only for data your
  application stored itself. `Proof`, `BlindedMessage` and `BlindSignature`
  still deserialize, parsing their points by their `keyset_id`.
- `verify_proof_signatures` checks a batch of proofs on any keyset version:
  DHKE DLEQ proofs for v1/v2 keysets, according to `LegacyDleq::Optional` or
  `LegacyDleq::Required`, and one batched pairing check for v3 keysets.
  `Proof::verify_signature` and `BlindSignature::verify_signature` do the same
  for a single item.
- `AuthToken::BlindAuth` now holds a `Box<BlindAuthToken>`, because the wider
  proof types made the variant large. Wrap values with `Box::new` when
  constructing it.
- `KeySetVersion` has a new `Version02` variant; update exhaustive matches.
- `Witness` gains a `Nutroot` variant. A v3 witness has the shape of a P2PK
  witness, so parse stored witnesses with `Witness::from_json_for_version`.
- `Proof`, `ProofV3` and `ProofV4` gain `spend_info`; `ProofState` gains
  `input_digest`; `AuthProof` gains `witness`; `BlindAuthToken` gains
  `request` and `signing_key`; `PaymentRequest` gains `nutroot`.
- `SendOptions` gains `nutroot`, `ReceiveOptions` gains
  `v3_min_refund_horizon` and `v3_payment_request`, and `CreateRequestParams`
  gains `nutroot`.
- `MintInfo`'s NUT-10 setting is now `Nut10Settings`, with `leaves`.
- The mint database traits gain `add_input_digests` and `get_input_digests`.
- `Wallet::verify_token_dleq` is deprecated. Use `verify_token_signatures`,
  which also verifies v3 proofs. The FFI wallet exposes both methods.

04Why BLS first

Pairings let the secret be shared later

Secp DHKE needs one operator and DLEQ. BLS verifies against one public key even if k is later split.

secp v1/v2 Y = H(secret) B_ = Y + rG C_ = k · B_ C = C_ − rK DLEQ proves knowledge of k BLS v3 B = r · H(secret) G1 C_ = k · B C = r⁻¹ · C_ e(C, G2) == e(H(secret), K) e(C_, G2) == e(B, K)

Mint keys live in G2 (96 B). Blinded messages and signatures live in G1 (48 B). DST: CASHU_BLS12_381_G1_XMD:SHA-256_SSWU_RO_.

07Deterministic derivation

HMAC for wallets, BIP32 then Fr* for mints

NUT-13 secrets reuse the v2 HMAC KDF for v3. Blinding factors add an attempt counter and parse as canonical BLS scalars.

"Cashu_KDF_HMAC_SHA256" || keyset_id || u64_BE(ctr) || 0x01 || u32_BE(attempt) → reject 0, accept Fr*

Mint amount keys evolved: hash child → reduce child → rejection-sample i' / attempt'.

for amount i: child = BIP32(i' / attempt') accept SecretKey::bls_from_slice(child)

08v3 proof life cycle

Blind check, then unblind, then proof check

  1. Wallet derives secret and r, blinds B = r · H(secret), sends ordinary Cashu outputs.
  2. Mint signs C_ = k · B and attaches no DLEQ.
  3. Wallet checks e(C_, G2) == e(B, K), unblinds C = r⁻¹ · C_, then e(C, G2) == e(H(secret), K).

Early wallet code skipped the blind pairing. 289fe9e44 wired verify_bls_blind_signature into mint-response, restore, auth mint, and verify_token_signatures.

09Mixed-curve safety

A valid G1 point is valid hex

Old secp helpers assumed every public key had an x-only form. A compressed G1 point in P2PK data used to panic.

  • P2PK / HTLC remain secp-only → NonSecp256k1Pubkey
  • Identity G1/G2 rejected
  • Zero scalars rejected for r, mint keys, batch weights
  • NUT-00 batch vector is a unit test
Fuzzfuzz_bls_pubkey_in_conditions injects real G1/G2 into nut10 fields. Random hex almost never hits a subgroup-correct BLS point.

14Alternative

Many secp signatures can fake a threshold

BLS is more elegant. It is not the only construction.

Each member could return a complete secp signature on the same blinded message. The proof would carry a set of them, like Bitcoin bare multisig: valid iff t advertised keys signed. That is a real federation. It just moves the threshold into the bearer object. BLS keeps the threshold on issuance and reconstructs one ordinary proof before the token exists.

Interpolated secp DHKE can produce one C, but proving it is k · Y without k needs threshold DLEQ. Bitcoin can afford bare multisig because the UTXO names its script. Cashu cannot, because the coin is the signature.

16Threshold scheme

Shamir on the blinded G1 point

Not many independent signatures. Not IETF multi-message aggregation. One k, any t reconstruct k · B.

f(x) = k + a1 x + … + a_{t-1} x^{t-1} k_i = f(i) K_i = k_i · G2 K = k · G2 B = r · H(secret) C_i = k_i · B e(C_i, G2) == e(B, K_i) λ_i = Π_{j≠i} (−j)/(i−j) C = Σ λ_i · C_i = k · B

Signer IDs are non-zero u16. 2-of-3 toy: f(x)=7+3x → shares 10, 13, 16. Any pair reconstructs 7B.

17Threshold-signing mix-and-match

Sliding window is the picture, not the name

A BLS share is independently valid. If members sign whatever they are shown, a wallet can collect t shares for more outputs than it paid for.

RFC wording: present different outputs to different members and combine overlapping share subsets. Tests slide ABC / BCD / CDA / DAB over one paid quote.

3-of-5, paid for 2, attacker wants A,B,C M1 M2 M3 sign {A,B} M4 M5 sign {B,C} then M3 also signs {B,C} each column now has 3 stars

18Consensus before signing

AlephBFT is a box that emits one envelope

Members do not sign because they received HTTP. They sign because that exact hashed swap came out accepted.

envelope = { federation, Swap, inputs:[P1,P2], outputs:[A,B] } operation_id = hash(envelope) S_AB and S_BC are different IDs one winner → spend P1,P2 and sign only A,B

Mint/melt conflict on quote ID. Swap locks by spending the input proofs. A 3-of-5 signing threshold under 4-of-5 BFT is safe only because shares are produced after accept.

19Data flow and transport

A star for wallets. A mesh for members.

HTTP and Iroh are pipes. iroh:// is the same Cashu and /federation/v1 traffic, not a new protocol.

Public plane: signing work fans the same request to every public_mint_url. Wallet aggregates any t valid shares. Quote creation is first-healthy, then threshold visibility.

Private plane: authenticated federation_api_url carries envelopes, Aleph messages, catch-up, and later DKG.

20BLS DKG

Commit, reveal, deliver, add

Dealer-free Pedersen DKG. Nobody ever holds k. The wallet still sees one v3 keyset.

f(x) = Σ f_j(x) K = Σ C_j[0] = k · G2 k_i = Σ f_j(i) check: f_j(i)·G2 == eval(C_j, i)

Hash first so the last member cannot adapt. Reveal G2 coefficients. Privately send evaluations. Sum. Transcript + activation before anyone signs eCash.

21Challenges

Consensus does not bind client intent

Open critical: SEC-2026-07-17-01. One Byzantine member can spend the wallet’s bearer proofs first.

Still a production blockerThe envelope is authorized as “a roster member said this swap should happen,” not “the owner of these proofs wanted these outputs.”
wallet fans P1,P2 → A,B evil M5 copies proofs, submits P1,P2 → X,Y if that envelope wins, honest members sign X,Y wallet’s {A,B} dies as TokenAlreadySpent

NUT-11 SIG_ALL is the Cashu-shaped fix: the owner’s witness commits the exact outputs. Fan-out is how the evil member learns the proofs. DKG protects k, not the user’s secrets.
